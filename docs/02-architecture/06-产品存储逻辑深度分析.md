## 一、核心模型：三层产品体系

产品域共 14 张表，围绕一条主线组织：**RSPU（款式）→ 变体（规格组合）→ RSKU（工厂报价）**，外加图片、向量、关系、字典治理四类附属数据。

```
                         category_dict (dict_type, dict_code) 复合主键
                          ▲ 复合FK                ▲ 复合FK
                          │                       │
  ┌────────────────── rspu_style ──┐   ┌── rspu_scene ──┐
  │  (rspu_id, style_code) PK      │   │ (rspu_id, scene_code) PK
  │  is_primary 主风格标记          │   │ 场景不分主次
  └────────────────────────────────┘   └────────────────┘
                          ▲                       ▲
                          │ 1:N                   │ 1:N
┌─────────────────────────────────────────────────────────┐
│ rspu_master (rspu_id VARCHAR(64) UUID 主键)              │
│ rspu_code 业务编码 UNIQUE（FS-MC-001-M，纯展示）           │
│ external_code 外部编码（部分唯一索引，导入查重）            │
│ 8 个 JSONB 标签列 + status/review_status/deleted_at       │
└─────────────────────────────────────────────────────────┘
   │1:N                │1:N                │1:N           │1:N
   ▼                   ▼                   ▼              ▼
rspu_variant      rsku_supply        image_assets    ai_recognition
(variant_id PK)   (rsku_id PK)       三向可空归属      只增审计表
尺寸×颜色×材质      rspu_id NOT NULL   +content_hash    encode/label/judge
"码或原文"判重      variant_id 可空     +is_primary
uk_variant_attrs  factory_price AES
                  idx_rsku_unique ──► price_history（密文历史）

rspu_factory_mapping  N:M（UNIQUE(rspu_id, factory_code)，合作层面登记）
factory_variant_capacity  N:M（复合PK factory_code+variant_id，产能到变体级）
rspu_relation  自引用 N:M（official / ai_verified / exclude）
```

三个发号计数器表全部用 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 单条 SQL 原子递增，**无应用层序列，并发发号安全**：

| 计数器表 | 发号维度 | 生成内容 |
|---|---|---|
| `rspu_code_counter` | (category_code, style_code) 复合 PK | rspu_code 第 3 段流水（上限 999） |
| `variant_code_counter` | rspu_id 单列 PK（FK） | `{rspu_id}-V{seq:03d}` |
| `rsku_code_counter` | (rspu_code, factory_code, material_code) | rsku_code 第 7 段流水 |

另有 `order_no_counter`（订单每日序号），同模式。

## 二、三层各自的存储语义

### 2.1 第 1 层 rspu_master —— "这个款是什么"（设计概念层）

表头注释（V1 L20）："款式概念，**不含工厂/价格/SKU 信息**"——铁律在 DDL 层无法违反。

关键列（V1 L21–52）：

| 列 | 类型 | 说明 |
|---|---|---|
| `rspu_id` | VARCHAR(64) PK | UUID 主键（`RSPU-<36位UUID>`，V10 拓宽），被全库 15+ 处 FK 引用 |
| `rspu_code` | VARCHAR(32) UNIQUE | 业务编码 `FS-MC-001-M`，纯展示/报表字段（V20，ADR-004/007） |
| `external_code` | VARCHAR(64) | 外部编码；`uk_rspu_external_code` 部分唯一索引（`WHERE deleted_at IS NULL AND external_code IS NOT NULL`，V24，带存量重复预检 WARNING 跳过） |
| `category_code` / `category_path` | VARCHAR(16) / TEXT | 品类码 / 品类路径 JSON 数组 |
| `positioning_label` | VARCHAR(64) | 主风格/主职级（≈ rspu_style 中 is_primary 行的冗余，应用层维护） |
| `product_name` / `description` | VARCHAR(256) / TEXT | 商品名称（V21）/ 长文本描述原文（V25） |
| `retail_price` | NUMERIC(14,2) | 零售参考价，**不加密**（V25；V38/V39 售价解析链首选来源） |
| `status` / `review_status` | VARCHAR(16) | active/discontinued/draft ；待复核/已确认/存疑 |
| `aesthetics_confidence` / `source_agent_version` | VARCHAR | AI 美学置信度 / 识别模型版本 |
| created/updated/`deleted_at` | TIMESTAMP | 软删三件套（`@TableLogic`） |

**8 个 JSONB 列分三类角色**：

| 列 | 存什么 | 写入方 | 角色 |
|---|---|---|---|
| `six_dim_tags` | 六维标签 `{"A":...,"B":...}`，值为带品类前缀字典码 | AI 识别 + 人工微调 | AI 产出层；**GIN 索引（jsonb_path_ops）被列表筛选实际命中** |
| `style_vector` | 风格向量数组 | embedding 模型 | **向量副本层**（主存 ChromaDB，PG 副本用于回填重建） |
| `color_primary_hsv` | `[H,S,V]` | AI 看图提取 | AI 产出层 |
| `material_tags` | 款式级典型材质自由文本数组 | AI 识别/员工提炼 | AI 产出层（与 variant 材质是概括-明细关系） |
| `fabric_tags` | 面料标签字典码数组，DEFAULT `'[]'` | 录入/导入（V22） | 筛选层（走 fabric 字典码） |
| `scene_tags` | 场景标签数组 | AI 推断/导入 | **与 rspu_scene 双写冗余**（见 §六问题 2） |
| `budget_range` | `[下限,上限]` | 基于 RSKU 价格区间反推 | 展示层 |
| `key_specs` | 关键规格对象（框架材质、海绵密度等） | 员工提炼 | 展示层 |

索引：`idx_rspu_category(category_code,status)`、`idx_rspu_positioning`、`idx_rspu_review`、`idx_rspu_meta`（部分）、`uk_rspu_external_code`（部分唯一）、`idx_rspu_six_dim_gin`（GIN）。

### 2.2 第 2 层 rspu_variant —— "这个款有哪些具体规格"（物理事实层）

变体 = 尺寸 × 颜色 × 材质组合；变体编码 `{rspu_id}-V001` **刻意无业务含义**（表头注释：避免属性变化导致编码变更）。

关键列（V1 L99–119）：

| 列 | 类型 | 说明 |
|---|---|---|
| `variant_id` | VARCHAR(64) PK | `{rspu_id}-V{seq}`（variant_code_counter 发号，重试 3 次） |
| `rspu_id` | VARCHAR(64) NOT NULL FK | 所属款式 |
| `display_name` / `variant_code` | VARCHAR | 显示名（"兰卡沙发 2450mm A级布"）/ 业务变体编码（单人位/S/M/L） |
| `size_code` + `size_text` | VARCHAR(32) + VARCHAR(64) | 尺寸**归一码** + **工厂方言原文**（V26，"贵妃A位"） |
| `color_code` + `color_text` | 同上 | 颜色双轨 |
| `material_code` + `material_text` | VARCHAR(32) + VARCHAR(128) | 材质双轨（**产品事实**：这个变体是什么材质） |
| `dimensions` | JSONB | `{"w":560,"d":580,"h":780,"unit":"mm"}`，GIN 索引 |
| `material_mix` | JSONB | 多材质组合 `["实木框架","布艺座包"]` |
| `reference_price_band` / `product_level` | VARCHAR | 变体级价格带 / 等级（继承/覆盖 RSPU） |
| status + 软删三列 | | |

核心约束（V1 L680–687，V12 初建、V26 升级）：

```sql
uk_variant_attrs: UNIQUE (rspu_id,
  COALESCE(size_code, size_text, ''),
  COALESCE(color_code, color_text, ''),
  COALESCE(material_code, material_text, ''))
WHERE deleted_at IS NULL
```

**"码或原文"判重语义**：归一成功按码判重、归一失败按原文判重；未归一原文自动采集进 `dict_unresolved_value`（按 dictType+rawValue 查重累加 occurrenceCount）供运营渐进治理。应用层三处写入路径（`RspuVariantService.effectiveOf`、`ProductImportService.effectiveOf`、`ExcelAiImportService.effectiveOf`）与该索引严格对齐，并发兜底捕获 `DataIntegrityViolationException`。

### 2.3 第 3 层 rsku_supply —— "哪个厂多少钱能做"（供应报价层）

关键列（V1 L301–335）：

| 列 | 类型 | 说明 |
|---|---|---|
| `rsku_id` | VARCHAR(64) PK | UUID 主键 |
| `rsku_code` | VARCHAR(64) UNIQUE | 业务编码 `FS-MC-001-M-A004-PE-001`（V20） |
| `rspu_id` | VARCHAR(64) NOT NULL FK | 铁律：必须关联 RSPU |
| `variant_id` | VARCHAR(64) **可空** FK | 关联具体变体（语义见 §2.4） |
| `factory_code` | VARCHAR(16) NOT NULL FK | 工厂代码 |
| `factory_sku` | VARCHAR(64) | 工厂原始编码 |
| `factory_price` | **TEXT** | 出厂价，**AES-256-GCM 密文**（EncryptTypeHandler） |
| `price_band` | VARCHAR(16) | 由价格自动分档（<1000 low / <5000 mid / else high） |
| `material_code` | **VARCHAR(8)** | **编码属性**：rsku_code 第 6 段材质版本码（PE/LE/TN 2 位、办公 3 位），强制标准短码；缺失时回退继承变体材质码 |
| `material_description` | TEXT | 工厂详细材质说明（自由文本） |
| `lead_time_days` / `moq` / `warranty_years` | INT | 交期 / 起订量 / 工厂级质保（覆盖 RSPU 典型值） |
| `shipping_from` / `shipping_warehouse_id` | | 发货地（展示用）/ 发货仓库 FK |
| `structure_strength_rating` / `flame_retardant_capability` | VARCHAR(32) | 结构强度 / 阻燃能力 |
| `factory_photo_path` | TEXT | 工厂实拍图直存路径（**遗留字段，与 image_assets 体系双轨**） |
| `factory_credit_score` / `on_time_rate` / `quality_return_rate` | | 履约评分/准时率/退货率 |
| `quote_confidence` / `review_status` / `price_updated` | | 报价置信度（V11 字典）/ 复核状态 / 价格更新日 |

**两处 material_code 语义差异**（易混淆点）：

| | `rspu_variant.material_code`（VARCHAR(32)） | `rsku_supply.material_code`（VARCHAR(8)） |
|---|---|---|
| 角色 | **产品事实**：变体是什么材质，参与变体判重 | **编码属性**：报价的材质版本码，进 rsku_code |
| 值域 | 字典归一码（可空）+ 方言原文列，渐进治理 | 标准化短码，录入即要求归一 |

### 2.4 variant_id 可空的业务含义与共存机制

`rsku_supply.variant_id` 可空 + `rspu_id` NOT NULL，表达**报价可以先款后变体**：

1. 工厂报价单只到"款"不到规格时（Excel 导入早期、工厂统一报价），RSKU 只挂 RSPU；
2. 单规格产品无需建变体；
3. 导入流水线中变体匹配失败的过渡态。

唯一约束 `idx_rsku_unique(rspu_id, variant_id, factory_code) WHERE deleted_at IS NULL` 是共存关键，但 **PostgreSQL 唯一索引中 NULL 互不相等**——variant_id 为 NULL 时约束完全失效（见 §六问题 1）。应用层由 `RskuService.upsertRsku` 三元组预查兜底。

同时 `rspu_id` 与 `variant_id` 存在传递冗余（variant 自身带 rspu_id）：直存 rspu_id 让 NULL variant 行仍能定位款式、比价查询免 JOIN；代价是理论上可能出现 `rsku.rspu_id ≠ rsku.variant.rspu_id` 不一致，DDL 无约束，靠应用层校验（"变体不属于该产品"）。

### 2.5 附属表

- **`price_history`**（V1 L338–347）：只增不改（无 updated/deleted），`old_price/new_price` 同为 AES 密文；三个写入触发点——手工调价（`RskuService.updateRskuPrice`）、Excel upsert（reason="Excel 导入更新"）、批量导入（reason="批量导入更新"）；新建 RSKU 不记历史。
- **`image_assets`**（V1 L350–372）：三向可空归属（rspu/variant/rsku）+ `image_type`（white_bg/factory_photo/detail/original，代码另有 floor_plan）+ `is_primary` + `content_hash`（SHA-256，V31）；索引覆盖 (rspu_id,image_type)、(variant_id,image_type)、(rspu_id,is_primary)、(rsku_id)、(content_hash)。
- **`ai_recognition`**（V1 L394–416）：只增审计表（无 updated/deleted），recognition_type ∈ {encode, label, judge}，input/output JSONB 存原始请求响应，`parsed_*` 列存结构化结果——**原文与归一值刻意分离**。
- **`rspu_relation`**（V1 L375–389）：自引用 N:M，relation_type ∈ {official, ai_verified, exclude}；**无 (anchor,related,type) 唯一约束**，重复关系靠 status 区分。
- **`rspu_factory_mapping`**（V2）：款级合作关系（"这家厂能不能做这款"），UNIQUE(rspu_id, factory_code)，is_primary 主供工厂；与 rsku（变体级具体报价）分工明确。
- **`factory_variant_capacity`**：产能绑定到**变体级**（复合 PK factory_code+variant_id），monthly_capacity/current_booked/max_batch_size。

## 三、写入路径

### 3.1 三个录入入口（ProductService，全部 @Transactional）

| 入口 | 事务内写什么 | 特点 |
|---|---|---|
| AI 录入 `createEntry`（L102-229） | `rspu_master`（草稿 status=processing）+ `image_assets`（首张 white_bg+is_primary，写 content_hash）+ `async_task` | **不写**风格/场景/变体/RSKU——由异步 AI 补齐；content_hash 命中已有图片时拒绝（force 可跳过） |
| 工厂录入 `createFactoryEntry`（L242-285） | master → `assignRspuCode` → 默认变体 → 图片（挂 variant_id）→ `rsku_supply` | 不调 AI，一条事务全写完 |
| 手工录入 `createManualEntry`（L298-320） | 同上（无 RSKU） | 同上 |

**事务纪律**：
- 所有外部 IO（AI、embedding、图片下载、MinIO）都在事务外；
- 异步 AI 用 `TransactionSynchronization.afterCommit` 触发（`triggerAsyncProcess` L635-646），避免长事务持锁；
- `registerStorageRollbackCleanup`（L653-672）在回滚后删除已上传的对象存储文件，防孤儿文件；
- 发码/建变体/upsert RSKU 均标注 `noRollbackFor = BusinessException`，避免内层业务异常把外层事务标 rollback-only。

**rspu_code 生成**（RspuCodeService + RspuCodeMapper.xml）：`INSERT INTO rspu_code_counter ... ON CONFLICT (category_code, style_code) DO UPDATE SET sequence_value = sequence_value + 1 RETURNING` 原子发号；格式 `{category}-{style}-{seq:03d}-{size}`；尺寸码由 OCR 尺寸最大边按 600/1200/1800mm 阈值推断（S/M/L/X），推断码不在字典时按等级距离降级。

**变体创建时机**：

| 场景 | 逻辑 |
|---|---|
| 工厂/手工录入 | 无条件建 1 个默认变体 |
| AI 识别成功后 | RSPU 下无变体时创建；OCR 解析出 ≥2 个规格时展开建多变体 |
| 标准 Excel 导入 | 行内变体字段任一非空即建 |
| Excel AI 导入（有出厂价列） | 每个 factory 角色价格列 × 每个尺寸规格各建/复用一个变体并挂 RSKU |

### 3.2 异步 AI 识别落库（AiRecognitionPersistenceService）

核心策略 **"AI 只补空缺，不覆盖人工"**：

1. 字典归一：AI 中文名 → 字典码（`DictResolverService`，走 `category_dict.aliases` 同义词列，**精确匹配永远优先于别名**）；六维 E 值并入 material 候选；
2. 主表更新：`six_dim_tags`（归一为带品类前缀码）/`color`/`material_tags`/`scene_tags` 仅当人工未填时才写；`style_vector`、`aesthetics_confidence`、`source_agent_version` 始终更新；
3. 关联表：`refreshStyleAssociations`（主风格 is_primary=true + 备选）/`refreshSceneAssociations` 先查已有记录，**有则直接 return**；
4. 补发编码：识别成功且 rspu_code 为空时补发；推断不出尺寸/风格时标记 `review_status=存疑` 而不阻断；
5. 留档：`ai_recognition` 成功失败都记录（含原始 input/output JSONB）；
6. 图片置 `ai_processed=true`。

**两套别名机制分工**：
- `category_dict.aliases` 列（V22，TEXT 存 JSON 数组）= 字典运营预置同义词，服务**视觉识别/六维归一**；
- `dict_alias` 表（V27，uk(dict_type, alias_name)）= **Excel 导入链路的工厂方言运行时自学习**（resolve → 确认后 saveAlias 幂等写回）；
- 两者都未命中的原文进 `dict_unresolved_value` 采集表。

### 3.3 两条 Excel 导入链路

**标准模板导入（ProductImportService）**：EasyExcel 解析（≤500 行）；**逐行独立事务**（行失败只回滚本行）；`external_code` 双查查重（rspuId 与 externalCode 指向不同产品则报错）；更新模式空单元格不覆盖；风格/场景 delete+重建；变体按"码或原文"判重复用。

**AI 辅助导入（ExcelAiImportService，excel_import_batch/row 主链路）**：
- 批次两阶段：`previewMapping`（刻意无方法级事务，AI 调用在长事务外）→ `confirmAndImport`（`claimForImport` 原子抢占批次状态）；
- 行级处理 = 事务外 `prepareRow`（校验/三码容错/图片加载）+ 事务内 `persistRow`（master → 发码 → delete+重建风格场景 → mapping+变体+`upsertRsku` → 登记图片 → 建 AI 任务）；
- 同型号连续行自动归组到一个 RSPU，组内图片按 contentHash 去重，组内只建一个 AI 任务；
- 成功回写行记录 `generated_rspu_id/generated_variant_id/generated_rsku_ids/image_asset_ids/ai_task_id`；
- **行级覆盖图**（V33 `override_image_asset_ids`）：清洗页可为行指定覆盖图，优先级高于内嵌图和 URL 图；临时图存 `preview-images/{batchId}/`，导入时迁移正式路径；重导时 `preserveRowOverrideImages` 先备份再恢复。

### 3.4 图片登记

- 三向归属在代码中的维护：录入挂 rspu_id（手工/工厂录入同时挂 variant_id）；Excel AI 导入中锚在非图片列（如"规格/模块"列）的内嵌图记为变体级（挂 rspu_id+variant_id）；
- **`rsku_id` 归属列全代码库无任何写入点**（死列，工厂实拍图实际走 `rsku_supply.factory_photo_path` 遗留字段）；
- content_hash 三级查重：录入级全局拒绝（force 可跳过）→ 导入级同 RSPU 跳过重复登记（且库中已有主图时本轮不再设新主图）→ 组内批内去重；
- 主图约定分散在各写入路径：第一张为主图（white_bg+is_primary）；过小图（<200px）无主图资格；`strictPrimary` 模式（表格有明确图片列时只有图片列的图可升主图）；AI 主体裁剪后原图降级为 original。

### 3.5 价格链路

- **加密**：`EncryptTypeHandler`（AES-256-GCM，密文 = Base64(12字节IV + ciphertext + 16字节authTag)），密钥强制环境变量注入；解密对历史明文有兜底；存量迁移见 `migration/PriceEncryptionMigration`；审计日志对加密字段脱敏覆盖。
- **售价解析链**（`PricingService.resolveSalePriceDetail`，V38/V39）：
  1. `rspu_master.retail_price`（明文，来源 MANUAL）→
  2. 成本（解密 factory_price）× 品类倍率（`pricing_rule` 表，缓存 `pricingRule::all`，来源 CATEGORY_RULE）→
  3. 成本 × 全局倍率（`sys_config` 键 `pricing.markup.global`，缺省 2.5，来源 GLOBAL）→
  4. 都空则 NONE（未定价，订单/报价拦截）。
- **响应侧掩码**：`dataScopeHelper.canViewFactoryPrice` 为 false 时 factoryPrice 返回 null（设计师一律不可见，工厂管理员仅见本厂价）。

## 四、读取与检索路径

### 4.1 列表查询（ProductQueryService）

- **单表 + EXISTS 子查询**，不做物理 JOIN：

| 过滤条件 | SQL 形式 |
|---|---|
| 品类 | `category_code = ?` 直列 |
| 风格/场景 | `EXISTS (SELECT 1 FROM rspu_style/rspu_scene ...)` |
| 材质标签 | `material_tags @> ?::jsonb` |
| 六维 A/B/C/D/F | `six_dim_tags @> ?::jsonb`（**命中 idx_rspu_six_dim_gin**，筛选值存带品类前缀字典码，与归一写入对齐） |
| 供应商编码 | `EXISTS (SELECT 1 FROM rsku_supply ... factory_code LIKE)` |
| 主图有无 | `EXISTS/NOT EXISTS (... image_assets ... is_primary=TRUE)` |
| 关键词 | `category_path LIKE OR rspu_id LIKE` |

- **N+1 规避**：分页后固定 4 条批量 SQL（主图 URL / 工厂码 / 最低出厂价 / RSKU 数，`IN rspuIds` 一次拉取）。同样的批量模式用于 `RetrievalService.rerank` 与 `RspuRelationService.toResponses`。

### 4.2 三层检索（RetrievalService，POST /api/v1/retrieval/similar）

- 设计文档版（`01-整体架构.md` §九）：SQL 预筛 → 向量精排 → LLM 终审。
- **实际实现顺序不同**：ChromaDB 向量召回（metadata 层硬过滤 status=active + 可选品类，topK×5 放大候选池；风格刻意不在此硬过滤）→ 按 rspu_id 聚合取最优图 + SQL 复核 review_status → **规则重排融合**（"品类|风格|主色|材质"指纹跨 RSPU 同款去重 + 类别/风格/主色/材质/场景标签加权加成，封顶 0.20；六维一致加成默认关闭灰度）。LLM 终审未单独成层，降级为重排加成。

### 4.3 风格知识检索（StyleMatchingService）

独立于以图搜图链路：`style_matching_formula`（mustHave/compatible/avoid 公式，`@Cacheable("styleFormula")`）对 AI 识别结果做校验评分 → 落 `product_style_match`；六维评分从 `style_case` 成功案例读典型 forms/textures。`AiMatchingService` 的搭配推荐为"SQL 候选（30 条）→ LLM 挑选"两段式，不用向量、不读 style_case；`/api/v1/matching/recommend` 的"三层召回"是规划未实施。

### 4.4 数据权限贯穿

- `DataScope` 枚举：ALL / FACTORY_LIST / SELF_CREATED / PUBLIC_ONLY，由 JWT 过滤器填充请求级上下文；
- 工厂用户"自己的产品"视图 = `rsku_supply` 中本厂有报价的 RSPU 集合（`SELECT DISTINCT rspu_id ... IN`）；
- 非运营人员全库视图强制 `review_status='已确认'`；检索侧同样过滤；
- 搭配关系列表装配价格时做 `canAccessRskuFactory` 过滤，不泄露无权工厂的价格。

## 五、生命周期末端：删除与出单快照

### 5.1 删除链路（三级语义）

- **软删**（`deleteProduct` @Transactional）：数据权限 + 工厂归属二次校验 → master/variant/rsku/image/relation 五表 `@TableLogic` 软删；`rspu_style`/`rspu_scene` 无软删列**物理删除**（回收站恢复后风格/场景关联丢失，代码注释已明示此取舍）；记审计后发 `RspuDeletedEvent(rspuId, imageIds)`。
- **ChromaDB 同步**：`RspuDeletedEventListener` 用 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` 事务提交后异步删向量；**失败无重试**，靠 `VectorBackfillService` 回填自愈和彻底删除时的幂等补刀兜底。
- **彻底删除**（`permanentDeleteProduct`）：仅限已软删 + 未被 scheme_item 引用；按 FK 依赖顺序物理删 18 类关联数据（导入行 `generated_rspu_id/variant_id` 置空保留导入记录、price_history、ai_recognition、factory_variant_capacity 等），提交后删存储文件 + 再发删除事件清向量。

### 5.2 出单快照（两级冻结）

- **方案 scheme_item** = "活引用 + 价格快照"混合体：FK 引用 rspu/rsku/factory，同时冻结 `factory_price`（密文）/lead_time/moq/`space_tag`（V40 空间覆盖标签，NULL 时展示端回退产品首场景推导）；产品彻底删除被 scheme_item 引用拦截。
- **订单 design_order_item** = **全量冻结**（OrderService 由方案生成订单时）：`product_name`（product_name 优先回退 positioning_label）/`model`(=factory_sku)/`image_id`（主图）/`space_tag`（原样复制）/`list_price`（明文标准售价快照，V38）/`snapshot_json`（风格/颜色/材质/场景/keySpecs/交期/MOQ 打包，TEXT 存 JSON）。从此与产品主档完全解耦，产品删除/改价不影响已出订单。
- 成交价 = 标准售价 × 折扣率（`design_order.price_rate` CHECK [0,1]）。

## 六、产品域问题清单

### 需要关注的问题

1. **`idx_rsku_unique` 的 NULL 漏洞（数据正确性，建议优先修）**：`(rspu_id, variant_id, factory_code)` 中 variant_id 可空时约束完全失效，同厂同款可插入多条 NULL 变体报价。当前靠应用层 upsert 预查兜底，但预查+插入非原子，并发下仍可能漏。变体侧的 `uk_variant_attrs` 已用 COALESCE 解法，这里反而没有。建议：`COALESCE(variant_id, '')` 表达式索引或强制 NOT NULL。
2. **JSONB 标签 vs 关联表双写漂移风险**：`rspu_master.scene_tags` 与 `rspu_scene`、`positioning_label` 与 `rspu_style.is_primary` 行，无数据库级一致性保证；且两条写入路径语义不同（AI=增量补缺，Excel=delete+全量重建）。读模型/写模型分离是合理架构，但需明确"以哪个为准"并定期对账。
3. **ChromaDB 与 PG 向量双写顺序不一致**：主路径先 PG 后 Chroma（失败→任务降级 partial_success 不重试），回填路径先 Chroma 后 PG（PG 写失败补偿删除 Chroma）。`VectorBackfillService` 能自愈，但向量缺失期间以图搜图召回不到该产品。
4. **`image_assets.rsku_id` 是死列**：全代码库无写入点，工厂实拍图实际走 `rsku_supply.factory_photo_path` 遗留字段，图片体系双轨并存。
5. **回收站恢复不完整**：软删时 rspu_style/rspu_scene 被物理删除，恢复后产品丢失风格/场景关联，需人工补录或重新 AI 识别。

### 小问题

6. 注释/文档滞后：V1 L679 `uk_variant_attrs` 注释"V19 起"应为 V26；L32 `style_vector` 注释写"Ollama 生成 / 512 维"，实际 DashScope / 配置 1024 维；`image_type` 注释 4 值，代码已有第 5 值 floor_plan。
7. `rspu_relation` 的 `ai_verified` 类型在白名单中但无任何 AI 链路自动写入（设计预留）；表无 (anchor,related,type) 唯一约束。
8. 口径不一：Excel 报价导入路径强制要求变体编码（"变体编码不能为空"），与 DDL "variant_id 可空"的宽松设计不一致，建议文档明确哪条路径为准。
9. `material_tags @>` 筛选走 JSONB 包含谓词，但仅 `six_dim_tags` 有 GIN 索引，material_tags 无（数据量大后是潜在慢查询点）。

## 七、总结评价

**产品存储逻辑是整个项目设计最精良的部分**：

1. **三层模型职责分离干净**：款式（概念/AI 标签）→ 变体（物理事实/方言容忍）→ 报价（编码/加密价格）；铁律（master 无工厂价格）在 DDL 层无法违反。
2. **"码或原文"机制是处理脏数据的范式级方案**：不阻塞录入（方言照收）、保证判重（COALESCE 唯一索引）、渐进治理（dict_unresolved_value 采集 + dict_alias 自学习），DDL 约束与三处代码实现严格对齐。
3. **发号、判重、幂等全部下沉到数据库约束**：ON CONFLICT 原子发号、部分唯一索引、行级独立事务，并发安全不依赖应用层自觉。
4. **快照语义分级合理**：方案活引用+价格快照，订单全量冻结，历史不受产品演进影响。
5. **事务纪律统一**：外部 IO 不出事务、afterCommit 触发异步、回滚清理存储文件。

**核心风险集中在"双写"上**：JSONB 标签 vs 关联表、PG 向量副本 vs ChromaDB、factory_photo_path vs image_assets——三对双写都靠应用层约定维持一致性，缺对账机制；加上 `idx_rsku_unique` 的 NULL 漏洞，是产品域最值得优先修的一个数据正确性缺陷。
