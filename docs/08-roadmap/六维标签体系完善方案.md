## 一、背景与现状盘点

### 1.1 六维标签是什么

六维标签是用 A~F 六个固定维度描述 RSPU 产品形态特征的结构化标签，是"AI 看图识别 → 数字化档案"的核心产出之一。原始体系按座椅/沙发设计（轮廓/靠背/扶手/腿部/材质/软包），现已按品类扩展语义。

### 1.2 当前实现链路

```
AI 识别（VisionService）
  └─ SixDimSchemaConfig.buildPromptDescription(categoryCode) 按品类注入维度定义
  └─ AI 输出自由文本 sixDimTags: {"A":"一字型",...,"F":"填充饱满"}
写入（AiRecognitionPersistenceService）
  └─ rspu_master.six_dim_tags（JSONB，已有 GIN 索引 idx_rspu_six_dim_gin）
  └─ ai_recognition.parsed_six_dim（识别历史留档）
  └─ 只补空缺，人工/Excel 已填不被覆盖
消费
  ├─ 风格匹配评分（StyleMatchingService.evaluateSixDim，权重 0.20，模糊包含匹配）
  ├─ 前端展示（BasicInfoTab 按品类渲染维度名 / 录入结果页 A~F 列表）
  ├─ Excel AI 导入（sixDimTags 自由文本列）
  ├─ 详情页编辑（裸 JSON 文本框）
  └─ 字典管理（six_dim_A~F 六个类型，支持按品类 parentCode 维护）
```

### 1.3 当前数据现状（2026-07-31 实测）

- 库内 32 个 RSPU：SF（沙发）30 个全部有六维值，FS 2 个中 1 个有，其余品类无数据。
- 字典 `category_dict` 中六维仅有 `six_dim_A`、`six_dim_B` 各 3 条 FS 种子（A字架形/蛋形/方盒形、编织镂空/高背包裹/无靠背），C~F 为空。
- `category` 品类字典仅有 6 个品类码：FS/SF/TB/FC/BS/OF，**无 DT/BD/LT**。
- 实际识别值与字典种子完全脱节：如 `"宽厚扶手"`、`"中高靠背、轻微后倾"` 均不在字典中。

### 1.4 断点与问题（按影响排序）

| # | 问题 | 影响 |
|:--|:--|:--|
| P1 | **字典与 AI 输出脱节**：prompt 不约束六维输出，同义值泛滥（"宽厚扶手" vs "宽扶手" vs "宽厚弧形扶手"） | 无法筛选、无法统计、风格匹配只能靠模糊包含，准确率低 |
| P2 | **字典种子严重不全**：仅 A/B 两维、仅 FS 一个品类 | 字典管理中心 C~F 页签空白，管理机制形同虚设 |
| P3 | **GIN 索引闲置**：`idx_rspu_six_dim_gin` 已建但没有任何查询使用 | 产品库无法按形态特征筛选，"找出所有 L 型沙发"做不到 |
| P4 | **维度定义前后端双写**：`SixDimSchemaConfig.java` 与 `sixDimLabels.ts` 手工镜像 | 新增品类要改两处代码 + 发版，易漏改不一致 |
| P5 | **编辑体验差**：详情页六维编辑是裸 JSON 文本框 | 人工复核/修正容易写错键名和格式 |
| P6 | **品类覆盖不全**：床、餐桌、灯具等只有 GENERIC 兜底，B/C 维度语义牵强 | 非坐具品类识别质量无保障 |
| P7 | **E 维度与 materialTags 重复**：六维 E（表面材质）和材质标签描述同一属性却各自为政 | 数据冗余、可能不一致 |
| P8 | **字典主键不含 parent_code**：`category_dict` 主键为 (dict_type, dict_code)，多品类同名枚举值（如 TB/DT 的"直边"）无法共存 | 按"中文名即码"约定，V24 种子会直接主键冲突，必须先在编码规则层面解决 |

## 二、目标与价值

### 2.1 总目标

把六维标签从"AI 识别的展示性副产品"升级为**可归一、可筛选、可计算的形态特征基础设施**。

### 2.2 具体价值

| 价值点 | 业务场景 |
|:--|:--|
| **可筛选** | 产品库按"L型 + 宽厚扶手 + 落地式"组合筛选，选品效率质变 |
| **可归一** | 同义词收敛到枚举，维度分布统计（哪种扶手最多）成为可能 |
| **风格匹配提准** | 枚举值精确匹配替代模糊包含，风格判定置信度更可信 |
| **相似款/同款辅助** | 六维一致度作为向量检索的 rerank 信号，提升以图搜图与查重准确性 |
| **录入复核提效** | 结构化下拉编辑替代裸 JSON，人工复核从"写 JSON"变"选选项" |
| **品类可扩展** | 维度定义配置化，新增品类（床/餐桌/灯具）零代码上线 |

---

## 三、总体设计原则

1. **枚举归一 + 自由文本兜底**：AI 优先从字典枚举选择；无法归类时输出 `其他` 并保留原文，不丢信息、不阻断流程。
2. **字典驱动**：维度定义（schema）与维度枚举（字典）都落库/配置化，前后端从同一数据源读取，消灭双写镜像。
3. **按品类扩展**：schema 与枚举均以品类码（parent_code）隔离，新增品类即新增配置。
4. **渐进迁移，不破坏存量**：存量自由文本保留并可后台归一；所有消费方先兼容"枚举码 + 自由文本"混合态。
5. **复用现有机制**：字典 aliases 别名（V22）、字典管理权限（V23）、GIN 索引、启动期迁移（`migration/` 包模式），不引入新依赖。

## 四、分层实施方案

### 阶段 P0：字典体系补全（数据基础）

**目标**：六维字典六个维度、九大品类全部有可用枚举，且能无冲突落库。

**步骤 0（前置，必做）：补种品类字典**

`category` 字典当前无 DT/BD/LT，而 AI 识别的品类枚举来自 `VisionService.buildCategoryEnumText()`（读取该字典）——**不补这三条，AI 永远不会把产品识别为餐桌/床/灯具，三个品类的六维定义永远不生效**。V24 中先插入：

```sql
INSERT INTO category_dict (dict_type, dict_code, dict_name, sort_order) VALUES
('category', 'DT', '餐桌', 7),
('category', 'BD', '床', 8),
('category', 'LT', '灯具', 9)
ON CONFLICT (dict_type, dict_code) DO NOTHING;
```

**步骤 1：dict_code 编码规则（解决 P8 主键冲突）**

`category_dict` 主键为 `(dict_type, dict_code)`，不含 parent_code，多品类同名值（TB/DT 都有"直边"）无法共存。规则修订为：

- **dict_code = `{品类码}-{中文名}`**，如 `SF-宽厚扶手`、`TB-直边`、`DT-直边`（同名不同码，可共存）；
- **dict_name = 中文名**（如 `宽厚扶手`、`直边`），展示层统一走 `resolveDictName` 显示名；
- 六维值（`six_dim_tags`）存储 dict_code（带前缀），筛选/精确匹配用码，展示用名；
- 存量 6 条 FS 种子（`A字架形` 等无前缀码）在 V24 中一并规范化为 `FS-A字架形` 形式（UPDATE dict_code）；六维字典无 FK 引用、存量 six_dim_tags 实际值为自由文本不引用字典码，改码无下游破坏。

**步骤 2：生成 V24 种子**

新增迁移 `V24__six_dim_dict_seed.sql`，按"附录 A 枚举清单"补齐 `six_dim_A` ~ `six_dim_F`，每个维度 × 每个品类（FS/SF/TB/FC/BS/OF/DT/BD/LT）6~12 个枚举值，`parent_code` 关联品类码；每个值配置 `aliases` 常见同义词（电商/工厂/展会真实叫法）。清单行数约 400+，建议参照 `scripts/generate_style_knowledge_seed.js` 写生成脚本产出 SQL，避免手工誊写出错。

**步骤 3：E 维度不建独立枚举**

E 维度（表面材质）统一引用 material/fabric 字典（见 P3-⑤ 去重设计），V24 不含 six_dim_E 种子。

**步骤 4：同步三处**

按数据库同步约定，同时更新 `V1__seed_data.sql` 与 `reset_db.sql`，全部 `ON CONFLICT DO NOTHING` 保证幂等。

**验收**：字典管理中心 six_dim_A~F 页签均有数据且按品类分组展示；category 字典含 DT/BD/LT。

### 阶段 P1：AI 输出枚举化（源头归一）

**目标**：新录入产品的六维值 95% 以上落字典枚举，且识别成本可控。

1. `VisionService.buildUserPrompt` 扩展：像风格/材质一样，把对应品类各维度的枚举清单注入 prompt，要求 AI 每维**必须从枚举中选择**，无法归类输出 `"其他"`。
2. **token 成本控制**（v2.1 新增）：每品类 5 维 × 6~12 值，全量注入"枚举名 + 全部 aliases + 完整判别要点"会膨胀 2~4K token，推高成本并稀释风格/材质字段的输出稳定性。注入策略：
   - 每个枚举值只注入 `中文名（一句话锚点）`，锚点取自附录 A「视觉判别要点」压缩版（≤20 字）；
   - 完整判别要点与 aliases 存字典 `remark`/aliases 字段，仅供识别后归一与人工复核使用，不进 prompt；
   - E 维度注入 material/fabric 枚举（现有机制，不重复）。
3. 识别后归一兜底：`DictResolverService`（已有别名归一机制）对六维输出按 **dict_type + 品类 parent_code 限定范围**做二次匹配（需扩展支持 parent_code 过滤），命中枚举名/别名则替换为带前缀 dict_code，未命中保留原文并记日志（供字典运营补充）。
4. Mock 数据（`buildMockLabels`）同步改为枚举值，保持测试一致。

**验收**：新录入产品的 `six_dim_tags` 值全部命中字典或标记"其他"；未命中值有日志可查；单次识别 token 消耗与耗时较现状增幅 ≤ 30%（回归实测）。

### 阶段 P2：存量数据归一治理

**目标**：库存自由文本值批量收敛到枚举。

1. 新增启动期迁移 `SixDimNormalizationMigration`（参照 `migration/PriceEncryptionMigration` 模式）：
   - 第一轮：按品类 + 维度做枚举名/aliases 精确匹配（纯规则，零 AI 成本）；
   - 第二轮（可选开关）：剩余未命中值调 AI 批量归一，逐条映射到最近枚举；
   - 归一失败保留原文，输出对账报表（总数/归一率/未命中清单）。
2. 迁移前后用 `scripts/check_entity_db_fields.js` 对账。

**验收**：存量六维值归一率 ≥ 90%，未命中清单可导出人工处理。

### 阶段 P3：消费端增强（价值兑现）

**① 产品库六维筛选（最高优先）**
- 后端 `ProductListParams` 增加六维筛选参数（如 `dimA`、`dimC`、`dimD` 按需），利用已有 `idx_rspu_six_dim_gin` 索引做 JSONB 包含查询；
- 前端 `ProductListView` 筛选区增加"形态特征"分组：按当前品类动态加载对应维度的字典下拉（品类未选时禁用或提示先选品类）。

**② 详情页结构化六维编辑**
- `BasicInfoTab`/编辑表单：六维从裸 JSON 文本框改为"品类 schema 驱动的 6 个下拉框"（选项=字典枚举+"其他"），保存时组装 JSON；
- 录入结果页（ProductEntryView）同样改为可编辑下拉，支持"识别后即时修正"。

**③ 风格匹配提准**
- `StyleMatchingService.evaluateSixDim`：枚举值与 style_case 关键词的匹配从模糊包含改为"枚举精确 + aliases 精确"，权重与评分逻辑不变，减少误判。

**④ 相似款判定辅助**
- 以图搜图（RetrievalService）结果 rerank：向量得分 + 六维一致度（同维度枚举相同计 1 分，加权求和）作为次要排序信号，配置开关默认关，灰度验证后开启。

**⑤ E 维度去重**
- 六维 E（表面材质）与 materialTags 统一：prompt 中 E 维度直接引用 material/fabric 枚举；存储上 E 维值与 materialTags 同源，展示层不再重复显示。

### 阶段 P4：维度定义配置化 + 品类扩展

**目标**：消灭前后端双写，新品类零代码上线。

1. 维度 schema 落库：新增表 `six_dim_schema`（category_code, dim_key, label, description, sort_order）；种子内置现有 7 套 + v2.1 新增 3 套（DT/BD/LT），共 10 套定义。
2. 后端提供 `GET /api/v1/dicts/six-dim-schema?categoryCode=` 公开查询接口；前端 `sixDimLabels.ts` 改为运行时从接口获取（带缓存），删除静态镜像。
3. 字典管理中心增加"六维维度定义"维护入口（ADMIN/EDITOR）。
4. **过渡期说明（v2.1 修正）**：DT/BD/LT 的生效路径分两段——P4 完成**之前**，仍需按现有双写方式在 `SixDimSchemaConfig.java` 与 `sixDimLabels.ts` 中补充这三套 schema（附录 A 已给出维度设计，可直接转写）；P4 完成**之后**，schema 迁移入库，后续新品类才真正实现"只配字典零代码"。建议 P0 完成后顺手把 DT/BD/LT 双写补上（约 0.5 天），不必等 P4。

## 五、数据模型与兼容性设计

| 项 | 设计 |
|:--|:--|
| 存储字段 | 沿用 `rspu_master.six_dim_tags`（JSONB），值从自由文本逐步收敛为枚举码；**不新增列**，AI 原始输出始终在 `ai_recognition.output_data` 留档可追溯 |
| 字典编码 | dict_code = `{品类码}-{中文名}`（如 `SF-宽厚扶手`），dict_name = 中文名；存量 6 条 FS 种子在 V24 中规范化为前缀码 |
| 混合态兼容 | 过渡期值可能是枚举码也可能是自由文本，展示层统一走 `resolveDictName`（命中显示字典名，未命中原样显示） |
| 索引 | 复用现有 `idx_rspu_six_dim_gin`，筛选用 `@>` 包含查询，无需新索引 |
| 主键约束 | `category_dict` 主键 (dict_type, dict_code) 不变更（变更会破坏 rspu_style 等 FK），多品类同名靠前缀码区分 |
| 回滚 | 所有阶段互不影响：P0 纯数据、P1 仅 prompt、P2 只读原文写新值（原文在 output_data）、P3 增量功能、P4 配置化有静态兜底 |

## 七、附录 A：六维枚举清单（完善版 v2.1）

> dict_code = `{品类码}-{中文名}`（表格中只列中文名，生成种子时自动加前缀）；aliases 列常见同义词（电商/工厂/展会真实叫法）。
> E 维度统一引用 material/fabric 字典，不重复建设。
> v2.0 扩充说明：基于现实市场在售产品形态（淘宝/京东/1688/品牌 catalog/展会口径）全面核对扩充；新增 **DT 餐桌、BD 床、LT 灯具**三个品类；每个枚举值附「视觉判别要点」，压缩后可直接注入 AI prompt 作为判别锚点。

### A.0 通用标注规范（跨维度边界规则）

0. **编码规则**：dict_code = `{品类码}-{中文名}`；dict_name = 中文名；同名值跨品类各立条目（如 `TB-直边` / `DT-直边`）；种子 SQL 由生成脚本按清单自动产出。
1. **每维独立打标，允许跨维组合**：商品俗名（"大象耳朵""钓鱼灯""毛毛虫"）一律入 aliases，不固化进枚举码。
2. **悬浮判定**：支撑结构内收/透明归 **D 悬浮底座**；台面与支撑间可见缝隙但支撑形态正常归 **B 悬浮台面**。正面平视无法确认离地间隙时判落地。
3. **层级分工**：A 管俯视轮廓/整体剪影；C 管边缘截面工艺/连接构件；D 管座面（台面）以下支撑结构——三者不同层级，勿互判。
4. **材质词不设值**：纯材质表述（绒面/皮面/实木）归 E 维度；只有构成稳定可识别形态差异的（绗缝/拉扣/编织/镂空/褶皱）才按形态设值。
5. **兜底**：AI 无法归类输出"其他"并保留原文；每维末位统一"异形/其他"。
6. **程度差异值给锚点**：厚/薄、高/低等连续光谱值，判别要点必须给可操作的锚点描述（如"垫体是否外溢鼓出框架轮廓"），降低 AI 灰度误判。
7. **组合关系 vs 单件形态**：子母茶几/模块沙发等组合形态在照片上"一眼可见为组合"时 A 按组判，单件轮廓另计。
8. **跨维去重**：同一可见特征只在一个维度设值（如转盘归 B 台面、围边归 C 边缘、悬浮归 D 底座）；附录清单已按此原则去重，新增值时先检查是否与他维已有值重叠。
