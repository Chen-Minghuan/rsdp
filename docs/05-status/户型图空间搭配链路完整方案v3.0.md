## 1. 需求理解与总体设计

### 1.1 业务场景

员工/设计师拿到客户的户型图（CAD 导出的 PNG/JPG，或手机拍的简易平面图），上传到 RSDP。系统：

1. 识别图上有哪些空间（客厅、餐厅、卧室……），前期只关心**客厅**
2. 提取客厅的尺寸（开间 × 进深，单位 mm），以及面积
3. 员工确认/修正识别结果（人工校正环节，管理端为必经完整版；客户端为页内轻量确认）
4. 选择风格偏好、预算上限（可选）
5. 系统从产品库中按**尺寸硬规则**筛选候选，再由 **LLM 按风格协调性终审**，输出一套客厅搭配方案
6. 管理端：方案落入现有 scheme 体系 → 可转报价单 → 可转订单（商业闭环已通）
   客户端（官网）：方案脱敏展示（仅零售参考价）→ 内嵌留资 CTA → 线索进管理端跟进

### 1.2 双端总体链路（一套引擎、两个门面）

```
                        户型图(PNG/JPG)
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
   管理端 /api/v1/floor-plan/**      客户端 /api/v1/public/ai-match/**
   异步任务 + 落库 + 完整人工校正      同步调用 + 页内确认（现状）
              │                               │
              └───────────────┬───────────────┘
                              ▼
              ┌─────────────────────────────────┐
              │  FloorPlanMatchingService（新建） │
              │  尺寸硬规则 R1~R5 → LLM 终审      │
              │  → 规则兜底（唯一出口，双端共用） │
              └──────────────┬──────────────────┘
                             │
              ┌──────────────┴───────────────┐
              ▼                              ▼
     管理端：落 scheme + scheme_item    客户端：脱敏展示（仅零售参考价）
     → 报价单 → 订单                   + CtaLead 留资（source=ai_match）
```

### 1.3 核心设计原则（与项目既有文化一致）

1. **AI 识别 + 人工校正，不赌全自动**
   PDF 导入链路 5 轮实测迭代的教训：AI bbox 输出存在格式抖动（越界、漏检、幻觉）。户型图识别属于同类问题，人工校正环节是链路可靠性的一部分，不是临时补丁。管理端做完整校正（bbox 增删改），客户端做页内尺寸确认（现状已实现）。

2. **硬规则先行，LLM 终审**
   "沙发放不放得下"是几何数学问题，用规则引擎算；"这套产品搭不协调"是美学问题，交给 LLM。各司其职，不让 AI 做算术。

3. **一套引擎、两个门面，杜绝逻辑分叉**
   尺寸规则与搭配编排收敛到唯一的 `FloorPlanMatchingService`，管理端与客户端共用；尺寸解析正则抽到公共 util。任何一端不允许私写规则副本。

4. **管理端输出落到现有 scheme 体系**
   搭配结果落 `scheme` + `scheme_item`（带 spaceTag），天然获得：空间分区视图、报价单生成、订单转换、分享画布。新功能只是多一个"方案生成入口"，不重造下游轮子。

## 3. 数据模型设计（DDL）

新增迁移脚本 **`database/V36__floor_plan_module.sql`**（V34=platform_lead、V35=scene_dict_cover_image 已占用；三处同步纪律：V36 独立文件 + V1__init_db.sql + reset_db.sql，幂等可重复执行）：

```sql
-- V36: 户型图分析模块
-- 户型图分析批次（一次上传一条）
CREATE TABLE IF NOT EXISTS floor_plan_analysis (
    analysis_id      VARCHAR(64) PRIMARY KEY,          -- FPA-<UUID>（IdGenerator）
    image_id         VARCHAR(64) NOT NULL,             -- 户型原图，指向 image_assets
    status           VARCHAR(16) NOT NULL DEFAULT 'pending',  -- pending/analyzing/awaiting_confirm/confirmed/failed
    task_id          VARCHAR(64),                      -- 关联 async_task
    raw_result       JSONB,                            -- AI 原始识别结果（不动，留档）
    confirmed_rooms  JSONB,                            -- 人工校正后的空间列表（最终生效数据）
    scale_ratio      DECIMAL(10,4),                    -- 识别/人工确认的比例尺（像素:实际mm），可空
    source           VARCHAR(16) NOT NULL DEFAULT 'admin',  -- admin（管理端）/ public（官网匿名）
    error_message    TEXT,
    created_by       VARCHAR(64),                      -- 官网匿名来源可空
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMP,
    FOREIGN KEY (image_id) REFERENCES image_assets(image_id)
);

-- 空间识别明细（每个识别出的空间一行，人工校正就地更新）
CREATE TABLE IF NOT EXISTS floor_plan_room (
    room_id          VARCHAR(64) PRIMARY KEY,          -- FPR-<UUID>
    analysis_id      VARCHAR(64) NOT NULL,
    room_type        VARCHAR(32) NOT NULL,             -- 引用 room_type 字典（LIVING/BEDROOM/...）
    bbox             JSONB,                            -- {x, y, w, h} 归一化坐标 [0,1]
    width_mm         INTEGER,                          -- 开间（人工校正后为准）
    depth_mm         INTEGER,                          -- 进深
    area_m2          DECIMAL(8,2),
    dimension_source VARCHAR(16),                      -- ocr_text / scale_calc / ai_estimate / manual
    dimension_confidence VARCHAR(8) DEFAULT 'low',     -- high/mid/low
    dimension_text   VARCHAR(128),                     -- 图上尺寸标注原文（如 "4200×3800"）
    sort_order       INTEGER DEFAULT 0,
    deleted_at       TIMESTAMP,                        -- 人工删除误识别空间
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMP,
    FOREIGN KEY (analysis_id) REFERENCES floor_plan_analysis(analysis_id)
);
CREATE INDEX IF NOT EXISTS idx_fpr_analysis ON floor_plan_room(analysis_id) WHERE deleted_at IS NULL;

-- 搭配方案与户型分析的关联（方案溯源）
ALTER TABLE scheme ADD COLUMN IF NOT EXISTS analysis_id VARCHAR(64);
COMMENT ON COLUMN scheme.analysis_id IS '来源户型图分析批次，可空';
```

**v3.0 相对 v2.0 的 DDL 变更**：
1. 编号 V34 → V36（V34/V35 已被 platform_lead、scene_dict_cover_image 占用）；
2. `floor_plan_analysis` 新增 `source` 字段（admin/public），`created_by` 改为可空——为客户端匿名分析落库预留（P0 默认仅管理端落库，官网落库见 §4.6 策略 A/B 决策点）。

### 4.4 AI 识别设计——复用已实现方法

`VisionService.detectFloorPlanRooms()`（:1089）已实现 v2.0 §4.3 的全部设计：9 类空间枚举 system prompt（:1051）、bbox 归一化坐标输出契约、dimensionText 尺寸标注提取、`response_format: json_object` + max_tokens、parseBoundingBoxClamped 越界收敛、JSON 容错解析。

**本阶段仅做两件小事**：
1. `parseDimensionMm` 从 PublicAiMatchService 抽到 `util/Dimensions.java`（正则 `(\d{3,5})\s*[×xX*]\s*(\d{3,5})` mm 标注 + `(\d+(?:\.\d+)?)\s*m\s*[×xX*]\s*(\d+(?:\.\d+)?)\s*m?` 米标注 ×1000 换算），FloorPlanService 与 PublicAiMatchService 共用；
2. （可选）scaleText 比例尺提取的后处理——prompt 已要求输出 scaleText，当前未消费，P1 再做像素换算。

**尺寸提取三级优先级**（FloorPlanService 内实现）：

| 优先级 | 来源 | 实现 | confidence |
|---|---|---|---|
| ① | 图上尺寸标注 OCR | `util/Dimensions.java` 解析 dimensionText | high |
| ② | 比例尺换算 | scaleText + bbox 像素尺寸推算（P1） | mid |
| ③ | AI 估算 | 无标注无比例尺时由 LLM 按常见户型经验估算（单独一轮轻量调用） | low |

人工校正后 `dimension_source = manual`，`confidence = high`。

### 4.5 异步任务接入（按实际代码模式）

`AsyncTaskProcessor` 是**方法级分发**（非 switch）：新增 `processFloorPlanAnalysis(String taskId, String analysisId)` 方法，照 `processProductEntry` 模式——`claimPendingTask(taskId)` 原子认领（返回 0 表示已被认领，直接返回），处理步骤：读 analysisId → 取图 → `detectFloorPlanRooms` → 尺寸三级提取 → 写 floor_plan_room 列表 → analysis 状态 → awaiting_confirm。由 `FloorPlanService.analyze()` 建任务后调用。`async_task.task_type` 为 VARCHAR，写入 `floor_plan_analysis` 无需迁移。

**收割器接入（v3.0 补充核实）**：`AsyncTaskReaper` 对 async_task 的 pending/processing 超时收割是**按状态、与任务类型无关**的（AsyncTaskReaper.java:61-81），新的 `floor_plan_analysis` 任务类型**自动被覆盖，无需改动**。真正需要注意的是 `floor_plan_analysis.status` 本身：若 JVM 崩溃，async_task 会被收割标 failed，但 analysis 行会永远停在 `analyzing`——`FloorPlanService.getAnalysis()`（接口 2，前端轮询入口）必须在返回前**以 task 状态为准同步校正 analysis 状态**（task=failed → analysis=failed + error_message 透传），不为 analysis 表单独做收割。

## 5. 空间尺寸硬规则引擎（RoomDimensionRules）

### 5.1 客厅品类组合模板

```java
// 客厅方案必选/可选品类（品类码来自 category 字典）
LIVING_TEMPLATE = {
  required: ["SF"],              // 沙发（必选）
  optional: ["TB", "FC", "FS"],  // 茶几、电视柜(柜类)、休闲椅(座椅)
  maxPerCategory: {SF: 1, TB: 1, FC: 1, FS: 2}
}
```

### 5.2 筛选规则（按优先级依次执行）

```
输入：RoomDimension(widthMm, depthMm) + 品类候选集
│
├─ R1 面积分档
│    area < 12㎡  → 沙发长度上限 2200mm，不推 L 型
│    12~20㎡      → 三人位为主（1800~2400mm）
│    > 20㎡       → 可 L 型 / 3+1 组合
│
├─ R2 沙发长度约束
│    sofaWidth ≤ min(墙长 × 0.75, 开间 - 600mm过道)
│    （假设沙发墙 = 开间方向；人工校正 UI 允许用户指定朝向，P1 做）
│
├─ R3 深度核算（进深方向链式校验）
│    沙发深度 + 通道(350~450) + 茶几宽度 + 通道(≥600) + 电视柜深度 ≤ 进深
│    不满足 → 依次降级：去电视柜 → 换窄茶几 → 换小沙发
│
├─ R4 品类过滤
│    scene 含 LIVING（rspu_scene 关联）且 category_code 命中模板
│
└─ R5 数据质量过滤
     dimensions 非空（sizeText 经 SizeSpecParser 可解析的也算）
     且有 ≥1 条有效 RSKU 报价（rsku_supply 未软删）→ 保证可转报价单
```

**输出**：每品类 ≤6 条候选（按 product_style_match 风格得分 + 创建时间排序），总量 ≤30（对齐 AiMatchingService.MAX_CANDIDATES）。

### 5.3 LLM 终审（FloorPlanMatchingService 编排，扩展 AiMatchingService）

`generateRoomScheme` 新增重载，prompt 中注入空间尺寸上下文：

```
你是家具搭配专家。客户客厅尺寸为 {widthMm}mm × {depthMm}mm（约 {area}㎡）。
请从候选产品列表中挑选一套客厅搭配：1 款沙发 + 0~1 款茶几 + 0~1 款电视柜 + 0~2 款休闲椅。
候选产品均已通过尺寸校验，你只需判断风格、颜色、材质的搭配协调性。
{预算约束段（budgetLimit 非空时）}
输出 JSON：{"rspuIds": [...], "reasoning": "..."}
```

**降级链**：LLM 返回空 → 规则兜底（每品类取风格匹配分最高者组合，reasoning 注明"规则推荐"），保证永远有结果。

### 5.4 方案落库（管理端）

复用 `SchemeService.createScheme`：scheme 名自动生成「{客户/日期}客厅方案」，`scheme_item.spaceTag = 'LIVING'`，价格取 RSKU 最低价快照（沿用 copyFromTemplate 的价格快照语义），`scheme.analysis_id` 回填溯源。

客户端方案不落 scheme，仅脱敏展示 + 留资。

## 7. 产品库数据量评估与数据准备

### 7.1 数据量分级

**最小可用（能演示、效果不丢人）：约 50~80 个 RSPU**

| 品类（码） | 数量 | 尺寸覆盖要求 |
|---|---|---|
| 沙发 SF | 15~20 | 单人(<1m) / 双人(1.5~1.8m) / 三人(2~2.4m) / L型(>2.8m) 四档都要有 |
| 茶几 TB | 10~15 | 覆盖 1.0~1.4m 主流长度 |
| 电视柜 FC | 8~10 | 覆盖 1.6~2.4m |
| 休闲椅 FS | 5~8 | — |
| 边几（可并入 TB/FC） | 5~8 | — |

**舒适可用（搭配有选择感）：150~300 个 RSPU**
- 覆盖 3~5 种主流风格（建议：现代简约、侘寂、法式复古、原木/北欧、新中式）
- **每风格 × 每品类 ≥ 3 款**，否则风格筛选后经常凑不齐一套，LLM 终审被迫返回空

### 7.2 每条数据的必备字段（缺一就掉出链路）

1. **`dimensions`（宽深高 mm）——本链路的命门**。缺失优先级处理：sizeText 经 SizeSpecParser 自动解析 → 仍缺的列入补录清单
2. 主图（搭配展示）
3. 风格码 `rspu_style` 关联（AI 识别已自动打）
4. 场景关联 `rspu_scene = LIVING`（AI 识别已自动打，注意核验：部分产品可能只打了其他场景）
5. ≥1 条有效 RSKU 报价（否则方案无法转报价单）

### 7.3 数据体检 SQL（开工前先跑）

```sql
-- 1) 品类分布
SELECT category_code, count(*) FROM rspu_master
WHERE deleted_at IS NULL GROUP BY 1 ORDER BY 2 DESC;

-- 2) 尺寸非空率（命门指标，目标 ≥90%，按品类分组看）
SELECT m.category_code,
       count(*) AS total,
       count(v.dimensions) FILTER (WHERE v.dimensions IS NOT NULL) AS has_dim
FROM rspu_master m
LEFT JOIN rspu_variant v ON v.rspu_id = m.rspu_id AND v.deleted_at IS NULL
WHERE m.deleted_at IS NULL
GROUP BY 1;

-- 3) 客厅场景覆盖
SELECT count(DISTINCT m.rspu_id) FROM rspu_master m
JOIN rspu_scene s ON s.rspu_id = m.rspu_id
WHERE s.scene_code = 'LIVING' AND m.deleted_at IS NULL;

-- 4) 有报价率
SELECT count(DISTINCT m.rspu_id) FROM rspu_master m
JOIN rspu_variant v ON v.rspu_id = m.rspu_id AND v.deleted_at IS NULL
JOIN rsku_supply r ON r.variant_id = v.variant_id AND r.deleted_at IS NULL
WHERE m.deleted_at IS NULL;
```

### 7.4 风格知识库与户型图样本

- **风格库**：执行 `psql -f database/seed_style_knowledge.sql`（11 个风格 × 客厅正向案例 + 9 个失败案例 + 搭配公式），仅覆盖客厅，与前期范围精确匹配，P0 无需新增。扩展到餐厅/卧室时按 `docs/03-guides/04-风格数据库导入数据格式.md` 补数。
- **户型图测试样本**：5~10 张真实户型图（来源要杂：CAD 导出图 / 手绘拍照 / 中介户型图，带标注和不带标注的都要有），用于全流程实测与 prompt 迭代。
- **补数最快路径**：用已有的 **Excel AI 导入 + PDF 画册导入** 灌真实工厂数据——尺寸列被 SizeSpecParser 自动展开成结构化 dimensions，风格/场景/六维由 AI 自动打标。建议从展厅常备的 3~5 家工厂报价表/画册开始灌。

## 11. 验收标准（Definition of Done）

1. 上传 CAD 导出的户型图 PNG，系统识别出客厅并给出尺寸（OCR 有标注时准确率 ≥80%，以 10 张真实图实测为准）
