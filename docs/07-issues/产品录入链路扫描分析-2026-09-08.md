# 产品录入链路全面扫描分析（2026-09-08）

> 只读扫描报告，未做任何代码改动。覆盖 7 条录入场景：①AI 图片录入（含一图多产品拆分）②平台手工录入 ③工厂单条录入 ④传统 Excel 批量导入 ⑤Excel AI 导入 ⑥PDF 文档导入 ⑦RSKU 报价录入（单条/批量/Excel）。
> 问题严重度标记：🔴 功能性 bug / 🟠 数据一致性或资源风险 / 🟡 健壮性与口径问题 / ⚪ 技术债。

---

## 一、录入链路总览

| # | 场景 | 前端入口 | 后端入口 | 核心 Service | 落库表 | AI 挂接 |
|---|------|---------|---------|-------------|--------|--------|
| ① | AI 图片录入 | `ProductEntryView`（/entry） | `POST /products/entry`、`/entry/detect-regions`、`/entry/by-regions` | `ProductService.createEntry/createEntryFromStream` → `AsyncTaskProcessor.processProductEntry` | rspu_master(processing) + image_assets + async_task → ai_recognition + ChromaDB | ✅ 完整（裁剪→识别→风格→向量→同款检测→发号） |
| ② | 手工录入 | `ProductManualEntryView`（/products/manual-entry） | `POST /products/manual-entry` | `ProductService.createManualEntry` | rspu_master + rspu_variant + image_assets | ❌ 仅主图 AI 裁剪（同步、事务内） |
| ③ | 工厂录入 | `ProductFactoryEntryView`（/factory-entry） | `POST /products/factory-entry` | `ProductService.createFactoryEntry` → `RskuService.createRsku` | ② + rsku_supply + rspu_price_summary | ❌ 同② |
| ④ | 传统 Excel 导入 | `ProductImportView`（/products/import） | `POST /products/import`（同步） | `ProductImportService`（1051 行，行级独立事务） | rspu_master + rspu_style/scene + rspu_variant + image_assets + dict_unresolved_value | ❌ 无 |

**整体评价**：骨架健康——UUID 主键与业务编码分离、计数器原子发号、行级事务隔离、批次抢占/任务认领/收割器状态机、SSRF 防护、factory_price AES 加密 + 投影表体系、实体-DB 对账全绿，均体现了多轮修复的成熟度。短板集中在：**状态机末端收口（processing 永久卡点）、关联表写入覆盖不均、唯一约束 NULL/软删策略不统一、三条录入链路的重复实现与进度持久化策略分裂**。

## 二、逐场景分析

### 场景① AI 图片录入（新品录入 + 一图多产品拆分）

**链路**：上传（≤8 张/10MB，魔数校验）→ SHA-256 内容查重（force 可跳）→ RSPU 草稿（status=processing，待复核）→ 图片 insertBatch → async_task → afterCommit 投递 → `AsyncTaskProcessor`：原子认领 → 主体裁剪（文档/Excel 来源跳过）→ 品类自动判定纠正 → `VisionService.recognizeImage`（qwen3-vl-plus）→ OCR 后处理 → 风格评分 → embedding → `AiRecognitionPersistenceService.saveSuccess`（只补空缺、补发 rspu_code、联动 RSKU 补码、写 ai_recognition）→ 同款检测（cosine≥0.95 标记存疑）→ 默认变体初始化（OCR 多尺寸展开）→ ChromaDB 向量。前端 localStorage 持久化任务 + 1.5s 轮询。

**实现情况**：完成度最高的一条链路。容错体系成熟（JSON 截断流式恢复、bbox clamp、终态保护、收割器兜底、轮询代际令牌）。

**存在问题**：

1. 🟠 **异步线程 SecurityContext 丢失，AI 链路审计操作人全部为 "anonymous"**。`AsyncConfig.taskExecutor` 无 TaskDecorator；`AiRecognitionPersistenceService.updateRspu`/`markRspuAsDoubtful` 取 `SecurityOperatorContext.currentUsername()` 时 ThreadLocal 为空。AI 识别是每个产品的关键写操作，审计链断裂。任务 input_data 里有 createdBy 可直接取用。
2. 🟠 **两处 RSPU 更新绕过审计**：`AsyncTaskProcessor` 品类自动判定纠正（updateById 无 auditLog）；`flagDuplicateSuspect` 置「存疑」无审计（而 `markRspuAsDoubtful` 有 logReview，口径不一）。
3. 🟠 **收割器不联动 RSPU 状态**：`AsyncTaskReaper` 只把超时任务标 failed，RSPU 草稿永久卡 `processing + 待复核`，无重试入口。
4. 🟠 **AI 识别失败把 RSPU 置为 active**：`markRspuAsDoubtful` 直接 `status=active`（仅 reviewStatus=存疑），识别失败产品进入正常列表/检索，失败语义与状态机混淆。
5. 🟡 **区域拆分部分成功时客户端拿不到成功明细**：`createEntriesFromRegions` 第 N 个区域失败 → 整接口 500，已成功的 rspuId 不返回；前端重试 → 重复建档（流式路径无 contentHash 查重）。
6. 🟡 **同款检测/人工复核 last-write-wins**：RspuMaster 无 @Version，select-then-update 并发可互相覆盖。
7. 🟡 **saveSuccess 在 RSPU 不存在时仍写关联表**：refreshStyleAssociations/refreshSceneAssociations 对不存在 rspuId 插孤儿行。
8. 🟡 **主风格归一失败时备选风格被一并丢弃**（styleCode==null 直接 return，secondary 已归一也不写）。
9. 🟡 **AI HTTP 层无连接池**（SimpleClientHttpRequestFactory，每次新建 TCP）；**同一任务 input_data 被 4 个方法各自 selectById + JSON 解析**。
10. 🟡 **图片查重的信息泄露与竞态**：报错文案跨数据归属暴露他厂产品名/编码；`idx_image_content_hash` 非唯一，并发同图双发可穿透。
11. 🟡 **前端**：entry 页轮询错误直接置任务 failed（两个 store 已改用 pollError 字段，口径不统一）；localStorage 键不按用户隔离（换账号看到上一账号任务 → 误标失败）；`clearAll` 有 pending 任务无二次确认；localStorage 无容量上限。

### 场景② 平台手工录入

**链路**：单页表单 → `createManualEntry`（@Transactional）：品类字典校验 → 插 RSPU（active/待复核）→ 发 rspu_code → 默认变体（三码"别名→字典→原文降级"）→ 图片入库 + **同步 AI 主体裁剪**。**不调识别、不算向量、不入 ChromaDB**。

**存在问题**：

1. 🔴 **不传 sizeCode 时整单失败**：DTO/前端均标可选，但 `assignRspuCode → generateNextCode` 对空 sizeCode 抛"尺寸码不能为空，需显式传入或由 AI 推断"——本链路明确不调 AI，兜底不存在，错误文案还误导。
2. 🟠 **图片不写 content_hash**：自身不查重（同图可无限重复录入），AI 录入链路也查不到这些历史图；keepOriginal 分支把 null 继续复制给 original 资产。
3. 🟠 **DB 事务内同步调 AI 裁剪**：长事务占库连接，AI 慢/挂时录入超时；与 Controller/JavaDoc「不调用 AI」的声明矛盾；与 createEntry 刻意事务外裁剪的设计不一致。
4. 🟠 **主图裁剪在同扩展名（jpg）时覆盖原图**：原图键 `images/{imageId}.{ext}`，裁剪图固定 `images/{imageId}.jpg`；上传 jpg 时同键，"original 原图资产"实际指向裁剪图，**原图永久丢失**，且两行资产指向同一文件。（场景①③⑥共用此裁剪服务，同受影响）
5. 🟡 **不写 rspu_style/rspu_scene 关联表**：只写 JSONB 列，而产品列表风格/场景筛选走 `EXISTS rspu_style/rspu_scene` → **手工录入产品在风格/场景筛选下永久查不到**（需后续编辑产品才修复）。sceneTags 无字典校验，坏值静默入 JSONB。
6. 🟡 **回滚清理遗漏裁剪图文件**（只登记原始键，裁剪新键成孤儿）。
7. 🟡 **发号/改码无审计**：`RspuCodeService.assignCode`/`RskuCodeService.assignCode` 直接 updateById 改写业务编码无审计；裁剪改写主图行无 logUpdate——与「所有修改 RSPU/RSKU 的操作必须记审计日志」约定不符。
8. ⚪ 手工/工厂录入的产品**永久无向量、不可以图搜图/同款检测**，与 AI 录入产品能力不对等，无补偿/回填入口。
9. ⚪ 前端：表单无 beforeunload/路由离开守卫（误刷新全丢）；字典加载失败仅 console.error。
10. ~~🔴 **带图录入在本地磁盘存储下必败**~~（2026-09-08 阶段 1.1 实测时发现并已修复）：`storeEntryImages` 先 `storageService.store(image,...)`（LocalStorageService 走 `transferTo` 移走 Tomcat 上传临时文件），后主图裁剪 `image.getBytes()` 抛 `NoSuchFileException`。修复为一次性读入字节、存储走 `store(InputStream,...)` 重载、裁剪共用字节。此前因死锁挡在前面从未暴露；生产 MinIO 实现不受影响。

### 场景③ 工厂单条录入

**链路**：两步向导（产品信息+必填图 → 变体+首条 RSKU 报价）→ `createFactoryEntry`：工厂归属校验 → 同②流程 → `RskuService.createRsku`（等级继承、能力校验/自动扩展、材质解析、price_band 分档、tryAssignCode 容错发号、AES 加密、审计、投影重算）。

**存在问题**：

1. 🔴 **纯 FACTORY_ADMIN 必然失败（2026-09-08 已实测坐实）**：`createDefaultVariantForEntry → RspuVariantService.createVariant` 调 `assertCanAccessRspu`；`DataScopeHelper.canAccessRspu` 对 FACTORY_LIST 要求"本厂已对该 RSPU 有 RSKU 报价"，而新建 RSPU 此刻无 RSKU（RSKU 在变体之后创建）→ 抛"只能维护本厂已报价的产品"。**实测记录**：用 dev 种子 `factory` 账号（纯 FACTORY_ADMIN、绑定 TEST 厂）调 `POST /products/factory-entry` 与 `POST /products/manual-entry` 均返回 400「只能维护本厂已报价的产品」，事务完整回滚无残留——手工录入路径同样被波及（`product:create` 工厂有，但共用的建变体方法触发同一校验）。该接口 `@PreAuthorize` 目标用户正是 FACTORY_ADMIN，现有测试全部 mock 了数据权限层所以未暴露。
2. 🟡 **factoryPrice 缺 `@Positive`**：可提交 0/负出厂价直达 createRsku（服务层也不校验符号，仅 updateRskuPrice 查 `<0`，与 DTO `@Positive` 口径不一）。前端 `:min="0"` 与详情页报价 `>0` 口径不一致。
3. 同②的 1/2/3/4/5/7 全部适用（共用同一组私有方法）。
4. ⚪ 前端未用 `sixDimTags/keySpecs/shippingFrom/diffNotes/quoteConfidence` 等可选字段（能力未透出，非缺陷）。

### 场景④ 传统 Excel 批量导入

**链路**：模板下载（反射 @ExcelProperty 生成表头 + 填写说明 sheet）→ 上传（≤10MB 魔数嗅探）→ EasyExcel 同步解析 → 7 类字典预载（无 N+1）→ 逐行：归一 → validateRow → 行内/文件内双重查重 → 图片下载（SSRF 防护：DNS 全解析复检、禁重定向、魔数拒 SVG）→ 行级编程式事务：按 rspuId/externalCode 查已有（冲突显式报错）→ 新增（发号）或更新（空值不覆盖 + 数据归属校验）→ 变体判重/发号 → 图片落库。**不写 excel_import_batch，无批次留痕**。

**实现情况**：安全防护、查重、行级事务、测试（58 例）都扎实，是完成度较高的链路。

**存在问题**：

1. 🔴 **办公家具职级码（EX/MG/ST/PU/CO）无法通过校验**：只预载 style 字典校验定位标签，职级码在独立 grade 字典；`RspuCodeService.validateStyleOrGradeCode` 明确两者皆收。办公家具导入填 "EX" 直接失败——与 AGENTS.md 4.2 分类语义冲突的实质 bug。
2. 🔴 **场景标签完全不校验、不归一，脏码直接插 rspu_scene** → 撞复合 FK → 行回滚；且 `DataIntegrityViolationException` 一律翻译成"产品编码或外部编码已存在"，真实原因被掩盖，用户无法定位。
3. 🟠 **图片下载 OOM 风险**：`readAllBytes()` 先全量读进内存再检查 20MB 上限，恶意 URL 可撑爆堆。
4. 🟠 **同步长请求无批次留痕**：500 行 × 每图 40s 超时全在一个 HTTP 请求内串行，超时后结果不可知；导入历史无法追溯（仅散落审计）。
5. 🟡 **审计 snapshot() 漏 productName/description/retailPrice/fabricTags**；rspu_style/rspu_scene 删+重建完全不记审计。
6. 🟡 **更新模式改品类码后不刷新 rspu_code**（编码含旧品类段，无任何提示）。
7. 🟡 **「交期天数」列被解析但被静默丢弃**（模板还教用户填）；`dimensionsText` 是 AI 链路寄生字段。
8. 🟡 **图片在事务内存储，回滚产生孤儿文件**；跳过模式仍先下载图片且产生误导性失败明细。
9. 🟡 **successCount + failedCount ≠ totalRows**：failures 混有警告与真失败，前端三数对不上。
10. 🟡 图片不写 content_hash（重复导入每次追加重复副本）。
11. ⚪ MAX_ROWS=500 在整文件解析完后才检查；重复检测对失败行也占位；空标签写 `"[]"` 而非 null；`saveStyles` 有死参数。

### 场景⑤ Excel AI 导入（最重链路，5021 行单类）

**链路**：preview（SAX 流式枚举 sheet → EasyExcel 512 行上限 → 表头探测/双行表头/同名消歧 → AI 列映射 + 关键词兜底 + 价格列材质角色 → 品类批量 AI 归一 → 存原始文件 + excel_import_batch）→ 数据清洗（单元格编辑/跳行/行覆盖图/跨行克隆/懒加载缩略图）→ confirmAndImport（前置校验 → 原子抢占 claimForImport + 结果快照恢复 → 下填/编辑应用/内嵌图锚点对齐 → BatchImportCache 批次预加载 → 逐行：事务外 prepareRow+下载+存图 → 行级短事务 persistRow（RSPU upsert/发号/风格场景/变体×价格列展开/RSKU upsert+AES+price_history/图片 content_hash 查重/建异步任务）→ commit/rollbackRow 缓存一致性）→ 批次结果 + 品类别名自学习。异步识别走场景①管线（跳过裁剪，AI 只补空缺）。

**实现情况**：全项目打磨最深的模块——缓存幻影处理、状态机闭环、SSRF、字典四层兜底链、SizeSpecParser 保守展开均有针对性设计和注释。前端向导的超时批次恢复 + 双代际令牌防双轮询链是样板级容错。

**存在问题**：

1. 🔴 **updateIfExists 重导重复烧 AI 调用**：`registerImages` 把库中已有主图也返回非 null → update 模式行恒建 AI 任务；叠加下行问题，一个产品 N 个模块行重导 → N 次识别 + embedding + 同款检测 + ai_recognition_record（真金白银的成本）。
2. 🔴 **update 模式行不重置 currentGroup**：同产品模块行分组失效 → 每模块行走一遍多余 updateExistingRspu（审计膨胀）并各自触发重复 AI 任务。
3. 🔴 **updateIfExists 允许任何 product:import 用户覆盖他人共享主数据**：`findRspuByExternalCode` 无归属过滤，`updateExistingRspu` 无条件覆盖 categoryCode/有值即覆盖 productName/materialTags/sceneTags/sixDimTags。RSPU 是全局共享主数据，可被"填同一 externalCode + 勾选更新"篡改。
4. 🟠 **工厂数据归属用户导入新产品必然整行失败**（同场景③的 assertCanAccessRspu 陷阱：saveMapping 静默丢失、createVariant 整行失败），代码无注释说明此约束。
5. 🟠 **内存/磁盘风险**：500MB 上限 + 全量入内存 + MinIO 一份 + 内嵌图全量提取 + 预览图写 tmpdir（仅启动时清理 >2h）；同一文件三次全量解析。
6. 🟠 **pending 批次无生命周期管理**：预览后放弃的批次，原始 Excel、preview_rows 全量 JSONB、临时图永久残留；行回滚已存 MinIO 图片成孤儿。
7. 🟠 **无图行 RSPU 永远卡 status='processing'**（翻 active 只发生在 AI 识别路径）→ 永不上架官网、列表永远"识别中"。
8. 🟡 **行级 tracking 写放大**：每行约 13+ 条 SQL 只为行记录（updateStage 每次 selectById+updateById）。
9. 🟡 **行内残留 N+1**：dict_alias 逐值单查、dict_unresolved 每值 2 SQL、交期规则每价格列一次、rspu_price_summary 每 RSKU 重算（同行多价格列重复重算同 RSPU）。
10. 🟡 **预览列顺序随机**（JSONB keySet 不保序）；清洗页写操作不校验批次状态（importing 中可改，撞唯一键或丢覆盖图）；description/materialTags 无差别整列下填会污染无关行；isNoteOrEmptyRow 硬编码词启发式有误杀风险；对象存储 key 与批次主键不一致（EXCEL- vs BATCH-）；createAsyncTask 把 objectKey 塞进 originalFilename 字段；"系统异常: null" 文案。
11. 🟡 **审计缺口**：rspu_style/rspu_scene 删插、dict_alias 自学习、批次状态机变更均无审计。
12. 🟡 **前端**：刷新丢全部进度（Pinia 无持久化，tryRecoverImportResult 仅同会话内触发）；行图片「粘贴」未走串行链（lost update 风险，正是注释声称要防的问题）；STANDARD_FIELDS 硬编码需与后端手工同步；500 行上限前端无前置校验。

### 场景⑥ PDF 文档导入

**链路**：校验（魔数/≤50MB/≤200 页）→ 嵌入大图提取（面积≥20%、边长≥200px、2500 万像素上限）→ 全页 200DPI 渲染 → 每 5 页一批 AI 区域检测（截断流式恢复、bbox clamp、批失败逐页重试）→ 产品框清洗去重/场景图甄别 → 逐产品：边缘恢复 → 扩框 → 白边收紧 → `createEntryFromStream`（独立事务）→ 异步识别管线（合并页面 OCR，品名以页面文字覆盖）。

**存在问题**：

1. 🔴 **整体同步执行，大文件必然超时而后端继续建产品**：HTTP 线程内跑全部渲染 + 最多 40 批串行 AI 调用（60s×重试）+ 逐产品建档，前端 300s 超时后用户看到失败，产品照建；且 `createEntryFromStream` **只记 hash 不查重**，重传同一 PDF 整批重复。
2. 🔴 **全部页面位图常驻堆内存**：200 页 × ~15MB ≈ 3GB，整页渲染无任何内存防护（嵌入图有 OOM 兜底，渲染没有）。
3. 🟠 **无批次表**（batchId 只在返回值，不落库）：与 Excel 导入能力不对齐，无法追溯/恢复。
4. 🟡 PDF 被解析 3 次（数页/嵌图/渲染各 load 一次）；DocumentImportController 的 categoryHint 无入口校验（逐产品失败计 failure）；`pageImages.isEmpty()` 死分支；兜底品类码 "FS" 硬编码。
5. 🟡 前端：刷新丢进度；每个 pending 任务独立轮询（100 产品 = 每 1.5s 100 次请求），无批量状态接口。
6. ⚪ Word/PPT 导入不存在（Controller JavaDoc 声称可扩展 PPT，实际只有 PDF）；`ops/anchor_encode.sh` 是纯 stub。

### 场景⑦ RSKU 报价录入

**链路**：单条（产品详情弹窗，工厂管理员限本厂）/批量（变体×工厂笛卡尔积，≤20，逐组合独立事务）/Excel 导入（RskuImportService 预加载 5 Map 消 N+1）→ createRsku：存在性/归属/变体校验 → 等级继承（请求>变体>RSPU）→ 能力校验/自动扩展 → 材质解析 → price_band 分档 → tryAssignCode → AES 落库 → 审计 → 投影重算。改价写 price_history。

**实现情况**：写路径收口整齐（投影重算全覆盖）、价格掩码三处口径一致、批量部分失败有明细。

**存在问题**：

1. 🟡 **RskuController 全类无方法级 @PreAuthorize**，仅靠 SecurityConfig URL 规则兜底；DataScope 层 DESIGNER 按 ALL 放行且读写在数据范围层不分离——一旦 URL 规则/种子权限调整疏忽，设计师可写报价（当前不可利用，属防御纵深缺失）。
2. 🟡 **idx_rsku_unique 的 NULL 判重漏洞**：唯一索引中 variant_id=NULL 不参与判重，upsert 查重 `eq("variant_id")` 也匹配不到 NULL 行；项目已在 lead_time_rule 用 NULLS NOT DISTINCT 修过同类问题，此处未修，策略不统一。当前所有写路径 variantId @NotBlank 故为潜在洞。
3. 🟡 **updateRskuPrice 允许 0 价**（服务层 `<0` vs DTO `@Positive` 口径不一，文案"不能为负数"与实际不符）。
4. 🟡 **RspuFactoryMappingRequest 全无校验注解**（空 factoryCode 报"工厂不存在: null"）；saveMapping check-then-act 并发撞唯一索引无友好翻译；主供唯一无 DB 级保障。
5. 🟡 **price_band 阈值（1000/5000）三处复制**（RskuService/RskuImportService/ExcelAiImportService）且 Excel AI 侧注释与实现自相矛盾；resolveMaterialGradeCode 硬编码 9 个中文材质名应入字典体系。
6. 🟡 **rspu_price_summary.recalculate 口径**：active_rsku_count 计入 NULL 价行、不看 status（discontinued 参与 min/max）。
7. ⚪ 前端：RskuImportView 前端校验允许 .csv 但 accept 只列 xlsx/xls；factoryPrice 用 JS number 传 BigDecimal 有精度隐患。

## 三、跨链路系统性问题（按主题归并）

### 3.1 状态机末端收口（最高优先）
- RSPU `status='processing'` 有**三个永久卡点**：① 收割器标任务 failed 不联动 RSPU；② Excel AI 无图行不建任务永不翻转；③ 任务线程池拒绝/JVM 重启后无人重试。
- 识别失败置 active 使"失败"与"存疑"语义混淆。
- **建议**：收割器联动（标存疑 + 补 ai_recognition failed 记录）；无图行落库即置 active/待复核；提供"重新识别"入口（按 rspuId 重建任务）；失败不置 active。

### 3.2 三条链路重复实现
- `ProductImportService`（1051 行）与 `ExcelAiImportService`（5021 行）各自实现了 RSPU 落库/风格场景重建/变体判重发号/字典归一/SSRF 下载/审计，规则有两处独立副本且**已出现漂移**（scene 归一：一个不做、一个做但不校验；content_hash：一个写、一个不写；价格带：三处复制）。
- **建议**：抽共享 `RspuPersistHelper`（落库+关联+变体+发号+审计），字典归一与 SSRF 下载收敛单一实现；价格带阈值入常量/字典。

### 3.3 审计日志缺口
- 异步链路操作人全为 "anonymous"（SecurityContext 不传播）；
- 漏记点：品类自动纠正、同款存疑标记、rspu_code/rsku_code 发号改写、主图裁剪改写、rspu_style/rspu_scene 删插（全部链路）、dict_alias 自学习、批次状态机、导入 snapshot() 漏 4 字段。
- **建议**：任务 createdBy 显式传入持久化层（或 TaskDecorator 传播 SecurityContext）；漏记点逐一补 logUpdate/logReview。

### 3.4 权限与数据归属
- 🔴 工厂录入/工厂身份 Excel 导入踩 `assertCanAccessRspu` 死锁（场景③⑤）；
- 🔴 Excel AI 更新模式可越权覆盖他人共享主数据；
- 🟡 RSKU 写接口仅 URL 层鉴权；查重报错跨归属泄露他厂产品信息；excel-ai-import 的 GET 接口被 `GET /products/**` = product:read 与方法级 product:import 双重叠加。

### 3.5 数据库约束策略不统一
- `idx_rsku_unique` 未用 NULLS NOT DISTINCT（lead_time_rule 已修）；
- `rspu_code`/`rsku_code` 普通 UNIQUE 与软删不兼容（external_code 已改部分唯一）；
- 永久删除残留 `rsku_code_counter` 孤儿行；
- 半成品列：ai_recognition.model_version/prompt_version 从未写入；image_assets.width/height/quality_score 主路径不写；excel_import_row.parent_row_id/row_type='module' 未启用。

### 3.6 资源与生命周期
- 孤儿文件多源产生：行回滚已存图、裁剪新键、清洗页临时图、pending 批次原始文件、1297 张历史重复图（既有遗留）；无统一清理任务。
- 大批量同步 HTTP 长请求（传统 Excel / Excel AI confirm / PDF）三条链路都靠前端超时文案兜底；PDF 全页位图常驻堆内存。
- **建议**：confirmImport/PDF 导入异步批次化（复用 async_task + Reaper）；批次清理定时任务；PDF 改逐页流式。

### 3.7 前端体验一致性
- 进度持久化三链路三策略（entry 页 localStorage / 两个 store 纯内存刷新即丢）；
- 轮询错误处理两口径（entry 页置 failed vs store 的 pollError）；
- 轮询无批量接口（PDF 百任务轮询风暴）；
- 表单页无防丢失守卫；字典加载失败静默；
- **建议**：抽公共 `useTaskPolling` composable；store 持久化 batchId+step+taskIds 支持刷新恢复；新增 `GET /tasks?ids=` 批量接口；表单页加离开守卫。
