# 字典管理中心 —— 设计方案与分步实施计划

> 状态：待实施（用户确认后按步骤执行，每步一个提交）
> 日期：2026-07-30

## 一、背景与目标

### 背景

`category_dict` 是平台的"预置数据底座"，目前已有 **26 个字典类型**，直接决定 AI 识别质量：

- **AI prompt 枚举注入**：风格/场景/材质/面料的候选词运行时从字典读取（`VisionService.buildEnumText`）
- **识别结果归一**：AI 输出名称 → 字典码（精确 + 别名匹配，`DictResolverService`），匹配不上被丢弃
- **前端下拉选项**：录入表单、筛选器全部来自字典接口

### 现状缺口

| 维度 | 现状 |
|---|---|
| 查看 | 无统一界面，只能查数据库或在表单下拉里窥见 |
| 新增 | 仅产品详情页弹窗可单个新增材质/场景/面料（`POST /api/v1/dicts`，权限 `dict:create`） |
| 编辑/改名 | ❌ 无接口 |
| 别名维护 | ❌ 无接口（V22 加的 aliases 只能改 SQL） |
| 启停用 | ❌ 无接口（status 字段存在但无管理入口） |

### 目标

一个统一的**字典管理中心**页面：
1. 浏览全部字典类型及已存条目
2. 新增 / 编辑（含别名）/ 启停用条目
3. 被系统逻辑引用的枚举型字典只读保护，防止误改破坏业务流

## 三、后端设计

### 3.1 现有资产

- `GET /api/v1/dicts/{dictType}` —— 按类型列条目（已认证即可）
- `POST /api/v1/dicts` —— 新增条目（`dict:create` 权限）
- `CategoryDict` 实体已含 `aliases`（V22）
- `DictService.listByType` / `createDict`
- `DictItemResponse` 缺 `aliases`、`status` 字段

### 3.2 新增接口

| 接口 | 说明 | 权限 |
|---|---|---|
| `GET /api/v1/dicts` | 类型汇总：`[{dictType, count}]`，左栏数据源 | 已认证 |
| `GET /api/v1/dicts/{dictType}` | 响应扩展：`DictItemResponse` 加 `aliases`（List\<String\>）、`status` | 已认证 |
| `PUT /api/v1/dicts/{dictType}/{dictCode}` | 编辑：dictName / dictNameEn / aliases / sortOrder | `dict:update`（新增权限点） |
| `PATCH /api/v1/dicts/{dictType}/{dictCode}/status` | 启停用：`{status: active\|disabled}` | `dict:update` |

**明确不做**：
- ❌ 物理删除——字典码被 `rspu_master.material_tags`、变体 `material_code`、RSKU 业务编码等引用，删除会造成悬挂引用；只提供停用
- ❌ 修改 dictCode——编码是引用键，只允许新建不允许改码

### 3.3 关键实现点

1. **权限种子**：新增 `dict:update` 权限（新迁移 V23），绑定 ADMIN 角色（参照 V9 收藏夹权限种子模式），`SecurityConfig` 加 PUT/PATCH 规则（参照现有 `DICT_CREATE` 一行）
2. **缓存失效**：`DictService.listByType` 若有缓存（Caffeine），更新/启停用/新增后必须失效——AI prompt 注入与字典归一都走这条路，实施时先核实缓存现状
3. **停用语义**：
   - `listByType` 是否过滤停用项需核实现状——停用项应**不进** AI 枚举注入、**不进**前端下拉，但历史数据展示（字典码→名称解析 `resolveNameByCode`）**不受影响**
   - 建议：`listByType` 保持返回全部（管理界面要看到停用项），新增 `listActiveByType` 供 AI/表单链路使用；或加参数区分。实施时按现有调用点最小侵入选择
4. **别名读写**：aliases 在库中是 TEXT(JSON)，`DictItemResponse` 输出 `List<String>`，更新时校验为字符串数组；`DictResolverService` 已兼容
5. **审计**：字典变更记 audit_log（字典直接影响 AI 识别行为，可追溯）
6. **校验**：dictName 非空长度 ≤64；sortOrder 整数；status 枚举值校验；编辑不允许改 dictCode/dictType（路径参数即身份）

### 4.3 交互细节

- **左栏**：`GET /api/v1/dicts` 拉类型汇总，按四分组折叠展示（分组配置在前端常量），显示条目数；只读分组带 🔒 标记
- **条目表格**：编码/中文名/英文名/别名（NTags 展示）/排序/状态（NTag 彩色）；操作列：编辑、停用/启用；只读类型隐藏操作列 + 顶部 NAlert 提示"该类型被系统逻辑引用，仅供查看"
- **新增/编辑弹窗**（同一个）：编码（编辑时禁用）、中文名、英文名、**别名（NDynamicTags 动态标签输入）**、排序号
- **启停用**：NPopconfirm 确认；停用项整行置灰
- **六维标签**：six_dim_* 类型按 parent_code 分组显示所属品类
- **搜索**：按编码/名称/别名前端过滤
- **权限**：无 `dict:update` 的用户只读（按钮禁用），与现有权限矩阵一致

## 六、风险与注意

1. **AI 联动即时生效**：prompt 枚举注入每次识别实时读字典，新增/停用立即影响下一次识别——这是特性不是 bug，但要在页面上让用户意识到（可在页面顶部加说明条）
2. **别名是识别质量的杠杆**：别名维护是这个页面最有价值的功能，UI 上要给它足够存在感（单独列 + 动态标签编辑），而不是埋在表单深处
3. **停用而非删除**：所有"删除"诉求都引导到停用；历史数据解析不受影响
4. **缓存一致性**：实施 Step 1 时必须先确认 `DictService` 与字典相关缓存（Caffeine）的失效策略，否则会出现"改了字典 AI 还用旧词"
