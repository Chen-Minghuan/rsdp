# RSDP 营销 Agent MVP 产品需求文档

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V0.1（需求评审稿） |
| 产品定位 | 面向客户的家具智能选品助手 |
| 使用角色 | 客户为主，设计师可代客户录入与操作 |
| 第一阶段目标 | 验证需求结构化、真实产品匹配、多轮反馈修正及主体产品确认的业务闭环 |
| 文档状态 | 待业务、产品、研发共同评审 |

## 1. 项目背景

RSDP 已具备家具产品数字化管理的业务基础。营销 Agent 需要在现有产品数据之上，建立面向客户的智能交互入口，将自然语言需求转化为可检索、可修改、可追溯的结构化数据，并通过持续反馈完成产品筛选。

长期目标是实现全案自动选品、效果方案确认、自动报价及订单成交；MVP 阶段聚焦选品链路，不一次性建设完整交易系统。

### 1.1 当前业务问题

客户需求通常以口头描述、聊天记录或零散信息存在，设计师和销售需要反复沟通、手工整理并检索产品。产品数量较多时，筛选效率依赖个人经验；客户提出修改后，需要重复寻找和对比商品。单品确认与后续搭配、报价之间也缺少可复用的结构化结果。

### 1.2 产品价值

将客户沟通过程沉淀为持续更新的需求档案，以真实 RSDP 产品为基础进行推荐，通过反馈逐步收敛到客户满意的产品，并为后续全案搭配与交易提供可追溯的数据输入。

## 2. 产品目标与成功标准

### 2.1 业务目标

1. 降低客户和设计师整理需求、检索产品的人工成本。
2. 通过多轮反馈提高产品推荐的相关性与客户确认效率。
3. 形成可供后续全案搭配、报价使用的结构化需求和产品确认清单。

### 2.2 MVP 成功定义

客户能够从一段自然语言需求出发，在 Agent 辅助下补全关键约束，获得真实 RSDP 产品推荐，通过反馈修正需求，并最终确认至少一件符合需求的主体产品。整个过程应可恢复、可追溯，不得由模型虚构产品事实。

### 2.3 产品原则

- 真实产品优先：产品名称、尺寸、材质、价格等事实必须来自 RSDP 数据或业务服务。
- 客户确认优先：模型可以建议，不得擅自将推荐商品认定为客户已确认。
- 需求持续更新：保留已确认约束，只修改用户明确调整的条件。
- 渐进式选品：优先确认主体产品，后续再扩展配套产品和全案。
- 复用现有能力：产品主数据、鉴权及业务查询优先复用 RSDP，避免重复建设。

## 3. 目标用户与使用场景

### 3.1 客户直接使用

客户希望购买家具，但不熟悉产品标签和数据库检索方式。客户通过对话说明空间、预算、风格及偏好，Agent 主动补全信息并推荐候选产品。

### 3.2 设计师代客户使用

设计师将客户沟通内容录入系统，Agent 自动提取需求并生成候选产品。设计师可以修改结构化字段、筛选产品、记录客户反馈和确认结果。

**权限原则：** 客户只能访问自身授权的数据与产品范围；设计师代录行为需要保留操作者与客户归属，具体权限应复用 RSDP 现有鉴权体系。

### 3.3 典型场景

客户描述：“我想买一套现代简约的客厅家具，沙发浅色一点，预算两万左右，客厅大概 25 平方米。”

Agent 提取已知条件，并询问沙发形态、最大宽度等关键缺失信息。客户补充“直排、宽度不超过 2.8 米、最好是布艺”后，系统匹配真实产品。客户反馈“第二款不错，但希望颜色更暖一些”，Agent 保留尺寸和材质约束，更新颜色偏好并重新推荐。客户最终确认一款沙发，系统保存对应产品及规格，供后续选品使用。

## 4. MVP 范围

### 4.1 必须交付

| 编号 | 功能 | 范围说明 |
| --- | --- | --- |
| M01 | 会话管理 | 创建、查看、恢复和结束选品会话 |
| M02 | 需求录入与追问 | 自然语言输入、关键信息补全 |
| M03 | 需求结构化 | 字段提取、展示、编辑和版本保存 |
| M04 | 产品匹配 | 基于 RSDP 真实产品执行过滤与排序 |
| M05 | 候选推荐 | 产品卡片、关键规格和推荐理由 |
| M06 | 多轮反馈 | 确认、拒绝、修改偏好并重新推荐 |
| M07 | 主体产品确认 | 保存产品、规格、数量与确认状态 |
| M08 | 历史追溯 | 保存需求版本、推荐批次和反馈记录 |

### 4.2 首期不交付

- 全屋全品类自动搭配及复杂搭配规则引擎。
- AI 效果图与真实户型渲染。
- 自动报价审批和复杂价格计算。
- 订单创建、在线支付及交付履约。
- 基于客户数据进行模型微调。
- 自主执行无边界的复杂多智能体系统。

上述能力属于长期业务闭环，不作为 MVP 验收的前置条件。

### 4.3 试点品类

优先考虑沙发、餐桌、床等 Level 1 主体品类。最终试点品类以数据完整度和业务使用频率为依据确定；若某品类尺寸、价格或标签数据不完整，应优先选择数据质量达标的品类开展验证。

## 5. 核心业务流程

```text
客户 / 设计师输入需求
        ↓
需求理解与结构化
        ↓
主动追问缺失信息
        ↓
用户确认或编辑需求
        ↓
RSDP 产品匹配与排序
        ↓
展示真实候选产品
        ↓
客户确认或提出反馈
        ├── 修改偏好 → 更新需求版本 → 再次推荐
        └── 确认产品 → 保存主体产品清单
                              ↓
                    后续全案搭配与报价
```

### 5.1 流程说明

1. 创建会话并输入客户需求。
2. Agent 提取已知信息，对关键缺失条件进行追问。
3. 用户查看结构化需求并可手动修改。
4. 系统调用 RSDP 查询能力，执行硬条件过滤和相关性排序。
5. 展示少量高匹配度候选产品及推荐理由。
6. 用户确认、拒绝或提出调整意见。
7. 系统保存反馈，生成新的需求版本并重新推荐。
8. 用户确认主体产品，形成可恢复的确认清单。

## 6. 功能需求

### F01 会话管理

**需求描述：** 支持创建、查看、恢复和结束选品会话。每个会话关联客户、创建者、当前需求版本及会话状态，设计师代录时记录实际操作者。

**验收标准：** 用户退出后重新进入，能够恢复需求摘要、历史反馈及已确认产品；不同客户之间的数据不得越权访问。

### F02 需求理解与结构化

Agent 从自然语言中提取标准字段，不得将未提及的信息伪装为客户已确认的偏好。字段应包含值、来源及确认状态，必要时记录置信度。

**建议字段（逻辑示例，非最终数据库规范）：**

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| space_type | living_room | 空间类型 |
| target_categories | sofa | 目标产品品类 |
| style_preferences | modern_minimal | 风格偏好 |
| color_preferences | warm_beige | 颜色偏好 |
| material_preferences | fabric | 材质偏好 |
| budget_total | 20000 | 整体预算 |
| budget_category | 8000 | 品类预算 |
| dimension_constraints | width_max: 2800mm | 尺寸约束 |
| functional_requirements | easy_clean | 功能需求 |
| excluded_features | leather | 明确排除条件 |
| delivery_constraints | 指定交期 | 可选交付要求 |
| free_text_notes | 客户补充说明 | 未结构化的原始信息 |

字段命名、枚举、单位和产品属性映射最终应与 RSDP 真实数据库及业务字典对齐。预算需区分整体预算与品类预算，尺寸需明确单位和约束对象。

**验收标准：** 已明确的信息能够正确提取；未知字段保留未知状态；用户可以编辑字段，修改后能够保存新需求版本。

### F03 主动追问

Agent 优先询问影响选品的关键条件，例如品类、尺寸上限和预算。避免一次性提出过多问题，已明确的字段不重复询问。用户可以回答“不确定”，系统应保留未知状态，不强制填写所有可选条件。

**验收标准：** 缺少关键约束时能够合理追问；用户补充信息后可继续选品；不会因非关键字段缺失而无限追问。

### F04 产品匹配

系统依据需求执行结构化过滤、语义或标签召回及相关性排序。用户明确提出的尺寸上限、价格上限、品类和排除条件应作为可验证的硬约束；风格、颜色、材质倾向及使用场景可作为软偏好。对于“最好”“大概”等模糊描述，应结合语义判断或请用户确认，不得擅自转为绝对条件。

**验收标准：** 推荐结果均存在真实产品 ID；不得违反可验证的硬性条件；缺少必要产品数据时应采用明确的降级或排除策略；无匹配结果时说明原因并建议调整条件，不得虚构商品。

### F05 产品推荐展示

产品卡片至少展示主图、产品名称、款式或型号、关键规格、材质、价格状态、推荐理由和操作入口。价格缺失时显示“价格待确认”，不得自行编造。

每轮建议展示 3–5 个候选产品，允许查看更多；实际数量由试点测试和交互设计确定。推荐理由应关联真实产品属性及客户需求，而非生成无法验证的营销描述。

**验收标准：** 卡片信息与产品详情一致；可查看产品详情；推荐理由能够解释主要匹配条件；缺图、缺价等情况有合理展示方式。

### F06 反馈与需求修正

支持确认、喜欢或收藏、不喜欢及原因、修改价格尺寸颜色材质等条件，以及自然语言补充说明。反馈同时保存原始内容和结构化解释。

对于“这款不错，但希望更暖色”之类反馈，应保留已满足的尺寸、材质等条件，只修改颜色偏好。无法确定反馈含义时，应请求确认，不覆盖既有硬约束。被明确拒绝的产品应记录拒绝原因，避免无理由重复推荐；用户主动放宽条件或要求重新查看时可以重新纳入。

**验收标准：** 下一轮推荐体现最新需求；已确认约束不被无故清除；反馈与需求变更能够追溯；系统能正确关联“第二款”等上下文指代的具体产品。

### F07 主体产品确认

客户可以将产品加入确认清单，并选择具体规格、数量及确认状态。若规格尚未确定，应标记为待确认，不得视为最终可下单商品。支持修改、取消确认及继续选品。

**验收标准：** 确认清单准确关联真实产品与规格；可以恢复和修改；区分“款式已确认”和“规格已确认”；清单可作为后续搭配和报价的输入。

### F08 历史与可追溯

记录需求版本、每轮推荐产品、匹配条件、反馈原因、确认操作及操作者。保留足够的推荐上下文，便于解释客户修改偏好后推荐结果为何变化。

**验收标准：** 能够查看需求变更历史及对应推荐记录；会话恢复后仍可正确关联历史产品；关键业务操作有可追溯记录。

## 7. 页面与交互建议

### 7.1 选品工作台

主区域为对话，展示需求采集与追问；辅助区域展示当前结构化需求、已确认条件和可编辑字段。用户修改字段后，系统应清晰提示是否需要重新推荐。

### 7.2 候选产品区

展示真实产品卡片，支持查看详情、喜欢、不喜欢、修改条件及确认产品。每轮候选应保留批次信息，便于引用和反馈。

### 7.3 确认清单

按空间和品类展示已确认产品、待确认规格、数量及状态，并提供继续选品的入口。

移动端应采用纵向布局或底部抽屉，避免同时展示过多信息。具体视觉稿与组件方案在交互设计阶段确定。

## 8. 产品数据与业务规则

### 8.1 产品事实来源

产品名称、图片、尺寸、材质、颜色、价格及其他商品事实必须从 RSDP 产品数据或业务服务获取。模型负责理解、组织和解释，不作为产品事实的权威来源。

### 8.2 需求约束规则

- 明确硬条件不得被推荐排序绕过。
- 软偏好用于排序，不应误当作绝对排除条件。
- 用户明确修改条件时，以最新已确认需求为准，并保留历史版本。
- 需求发生冲突时应提示用户选择，不静默覆盖。
- 未知字段与“不限”应区分处理。

### 8.3 推荐结果规则

- 推荐仅使用用户有权访问的产品范围。
- 不得返回已删除、不可访问或不符合业务展示条件的产品。
- 价格、规格等关键字段缺失时，应明确标注并执行约定的降级策略。
- 推荐清单中的产品 ID、规格 ID 应与产品主数据保持关联。

## 9. 技术实现边界（供后续架构设计）

本章节仅定义产品对技术的要求，不预先锁定具体框架、模型或向量数据库。

### 9.1 逻辑能力

- LLM：意图识别、需求提取、追问生成、反馈解释和推荐理由表达。
- 需求状态管理：保存结构化需求、字段来源、确认状态和版本。
- 产品查询能力：复用 RSDP 现有产品服务，执行过滤与检索。
- 排序能力：依据约束、偏好及真实产品数据计算推荐结果。
- 会话持久化：保存对话、需求、反馈和确认清单。
- 前端交互：字段编辑、产品卡片、反馈操作和人工确认。

MVP 倾向采用单 Agent 编排与确定性工具调用，暂不要求多个独立 Agent 协作。最终部署形态及技术选型需结合真实仓库核查确定。

### 9.2 逻辑工具契约

以下为能力草案，实际 URL、HTTP 方法和 DTO 应在核对现有后端后确定。

| 工具能力 | 主要输入 | 主要输出 |
| --- | --- | --- |
| parseCustomerRequirement | 会话上下文、客户文本 | 结构化字段与待追问项 |
| updateRequirement | 需求版本、字段变更 | 新需求版本 |
| searchProducts | 硬约束、软偏好、分页 | 产品 ID、规格、匹配信息 |
| getProductDetail | 产品 ID / 规格 ID | 产品真实详情 |
| recordProductFeedback | 产品 ID、反馈类型、原因 | 反馈记录及需求变更 |
| confirmProduct | 产品及规格、数量 | 确认清单项 |
| getSelectionSession | 会话 ID | 当前需求、历史与确认清单 |

### 9.3 数据设计原则

新增数据围绕营销会话与客户需求展开，不修改现有产品主数据的归属规则。建议逻辑实体包括选品会话、当前需求、需求历史版本、推荐批次、推荐产品、客户反馈和确认清单。

是否新增实体表、复用现有表或使用 JSONB 保存部分结构化需求，应以现有 DDL 和业务域边界为准。产品关联应使用真实主键，并明确 RSPU 款式层与 SKU 规格层的关系。此处不预设数据库改造已经完成。

## 10. 非功能需求

### 10.1 性能与体验

普通会话、产品查询和推荐流程应具备可接受的交互响应；模型耗时较长时应提供明确的加载或流式反馈。具体响应时间、并发量和吞吐量阈值在试点数据规模及部署环境确定后制定。

### 10.2 安全与权限

复用现有身份认证与授权机制；服务端校验客户归属和产品访问范围；不得仅依赖模型或前端进行权限判断。日志应避免明文记录敏感信息，模型调用及第三方服务的数据处理需符合企业数据安全要求。

### 10.3 可靠性与降级

模型解析失败、检索超时、向量服务不可用或产品数据不完整时，应提供可理解的错误提示及可恢复流程。必要时允许使用结构化过滤或人工检索继续选品，不得以虚构结果掩盖服务故障。

### 10.4 可观测性

记录会话请求、工具调用、错误类型、耗时、检索结果数量及必要的推荐追踪信息。日志与业务记录应分离，避免将完整敏感对话无约束写入技术日志。

## 11. 验收与测试

### 11.1 功能验收清单

- 一段完整需求能够生成可编辑结构化数据。
- 缺少关键条件时能够主动追问。
- 推荐产品均来自真实数据库。
- 明确的硬约束不被违反。
- 客户反馈能够正确修改需求。
- 重新推荐体现最新需求。
- 已确认产品能够保存和恢复。
- 无结果、缺价格、缺尺寸等异常能够合理处理。
- 设计师代录及客户数据访问符合权限要求。

### 11.2 评估指标

建议建立人工标注的真实客户需求测试集，覆盖常规、模糊、冲突、无结果和多轮修改场景。评估指标包括：

| 指标 | 评估目的 |
| --- | --- |
| 关键字段提取准确率 | 需求理解质量 |
| 硬约束违反率 | 推荐合规性 |
| 推荐结果有效率 | 产品真实性与业务有效性 |
| 首轮推荐相关性 | 初始匹配质量 |
| 多轮反馈后的推荐改善程度 | 反馈收敛能力 |
| 主体产品确认率 | 业务闭环效果 |
| 平均选品轮次与耗时 | 用户效率 |
| 产品事实幻觉率 | 商品信息可信度 |

正式阈值在样本集和试点品类确定后制定，避免在无基线时承诺具体百分比。MVP 验收应同时覆盖功能正确性与真实业务试用，不以对话演示成功替代业务验证。

### 11.3 关键端到端场景

1. 正常需求：输入预算、尺寸和风格，完成推荐与确认。
2. 缺失信息：缺少关键条件，Agent 追问后继续推荐。
3. 多轮反馈：客户修改颜色、预算或尺寸，系统保留其他约束。
4. 冲突需求：客户要求同时存在冲突的条件，系统提示澄清。
5. 无结果：硬条件下没有商品，系统说明原因并提供调整建议。
6. 数据缺失：商品缺价、缺尺寸或缺图，系统正确展示或降级。
7. 会话恢复：退出后恢复当前需求、历史推荐及确认清单。
8. 权限校验：客户不能访问其他客户的会话或无权限商品。

## 12. 开发阶段与交付物

### 阶段一：数据与接口准备

核查现有产品查询 API、标签字典、RSPU/SKU 关系、尺寸与价格字段、权限体系。选择数据质量达标的试点品类，整理真实测试需求。

**交付物：** 数据能力核查报告、MVP 字段字典、接口契约、测试样本。

### 阶段二：核心 Agent 开发

实现会话管理、需求结构化、主动追问、产品查询工具和候选产品展示。

**交付物：** 可运行的需求到推荐流程、接口测试与基础评估。

### 阶段三：反馈与确认闭环

实现反馈结构化、需求版本更新、重新推荐、产品确认清单和历史恢复。

**交付物：** 完整 MVP 业务闭环、端到端测试报告。

### 阶段四：试点与优化

由客户或设计师使用真实需求进行测试，统计推荐质量、确认率和失败原因，针对数据、检索及交互进行优化。

**交付物：** MVP 验收报告、问题清单及第二阶段全案搭配建设建议。

## 13. 主要风险与依赖

| 风险或依赖 | 影响 | 应对方向 |
| --- | --- | --- |
| 产品数据不完整 | 推荐质量下降、硬条件难以校验 | 先核查数据完整度并明确降级策略 |
| 需求字段与数据库不一致 | 生成无法检索的标签或条件 | 建立真实字段字典和映射规范 |
| 模型虚构产品事实 | 客户误解价格、规格或材质 | 商品事实由工具提供并在输出前校验 |
| 反馈覆盖错误 | 丢失客户已确认约束 | 需求版本化、冲突处理及变更审计 |
| 产品权限边界不清 | 越权访问客户或产品数据 | 复用服务端鉴权与数据权限 |
| 业务范围膨胀 | MVP 交付周期和风险增加 | 严格区分首期与后续全案功能 |

## 14. 待业务与研发确认事项

1. 首期试点品类及真实产品数据完整度。
2. 客户与设计师的账号、归属及权限模型。
3. 需求字段字典、单位、枚举及硬软约束规则。
4. 价格字段来源、价格展示规则及缺失处理方式。
5. RSPU 款式确认与 SKU 规格确认的业务边界。
6. 推荐结果数量、确认状态及人工调整交互。
7. 测试样本来源、成功指标基线及正式验收阈值。
8. 现有产品查询、标签和向量化能力的复用范围。

## 15. 后续产品路线

### 第二阶段：全案搭配

在主体产品确认基础上，扩展 Level 2 配套产品推荐、产品组合规则、预算校验、效果图或场景化方案及反馈调整。

### 第三阶段：交易闭环

在方案确认基础上，接入价格、库存、交期和报价服务，逐步完成报价确认、订单创建、支付及后续履约流程。

## 16. 评审结论

当前会议内容足以启动 MVP 需求设计。第一期以“需求结构化、真实产品匹配、多轮反馈修正、主体产品确认”为验收边界，优先验证选品价值。完成数据及接口核查后，可进一步冻结字段字典、接口契约与开发任务，并进入实施阶段。

本 PRD 是业务需求基线，不代表已完成真实仓库核查，也不预先确定具体 Agent 框架、向量数据库或部署架构。后续技术架构方案应基于本 PRD 和 RSDP 当前实现进行设计。
